## 1. Изучение практики: что берём, чего избегаем

Для каждого источника — вердикт «берём / избегаем / недоступен» и почему.

### 1.1. `docs/PLAN-networking.md` — НЕДОСТУПЕН

- В репозитории ornis файла `docs/PLAN-networking.md` нет (каталог `docs/`
  содержит только `WASM_PIXEL_E2E.md`, `animation-design.md`, `quality/`, `rendering/`).
- Доступа к репозиторию Balaur из этого среза нет, найти файл там невозможно.
- Вердикт: **недоступен**. Если Юра даст доступ к Balaur или сам файл —
  следующий срез сверит дизайн с ним и дополнит документ.

### 1.2. Rollback-модуль и Recordings-панель Balaur — НЕДОСТУПНЫ

- По `PLAN.md` §l это образцы для L1 (rollback) и L2 (запись сессий).
- Доступа к коду Balaur нет, разобрать устройство модуля и панели невозможно.
- Вердикт: **недоступны**. Компенсация: L1 проектируем по GGPO/ggrs
  (открытая модель, §1.4), L2 — по формату «ввод + сид + версия + per-tick digest»
  (§4.4), что покрывает ту же функциональность (повтор + проверка).
  При появлении доступа — сверить и зафиксировать расхождения отдельным коммитом в док.

### 1.3. Photon Quantum — БЕРЁМ input-only ядро, ИЗБЕГАЕМ закрытость и привязку к движку

Что известно (открытая документация Photon: детерминированный движок,
predict/rollback netcode, ECS-архитектура, авторитет сервера):

- **Берём:** обмен только вводом, а не состоянием. Симуляция детерминирована,
  одинаковый ввод на одинаковом тике даёт одинаковое состояние у всех пиров.
  Это ровно модель v1 ornis (§4.1).
- **Берём:** предсказание локального ввода + rollback при приходе
  запоздавшего ввода соперника. Локальный игрок не ждёт сеть.
- **Берём:** требование детерминированных строительных блоков
  (математика, физика) как предусловия — совпадает с нашим предусловием
  (Strong Confluence + G8, `PLAN.md` §l).
- **Избегаем:** закрытый код и привязку netcode к конкретному движку/облаку.
  ornis делает открытый `crates/net` с трейтом транспорта (§4.6),
  без vendor lock-in.
- **Избегаем:** «магию без цены» — Quantum скрывает сложность;
  мы фиксируем явно: границы солверов, одна архитектура у пиров в v1,
  реакцию на десинк (§4.3, §4.5).

### 1.4. GGPO / ggrs — БЕРЁМ rollback-скелет целиком

Что известно (GGPO — эталон rollback для файтингов; ggrs — Rust-реализация:
сессии P2P, задержка ввода, per-frame checksum, save/restore/advance):

- **Берём:** три операции как интерфейс отката: сохранить состояние тика,
  загрузить состояние тика, продвинуть симуляцию на один тик с заданным вводом.
  Это станет ядром L1: снапшот мира + restore + пересимуляция (§4.3).
- **Берём:** настраиваемую задержку ввода (input delay): локальный ввод
  применяется с задержкой в N тиков, чтобы снизить частоту предсказаний
  и откатов. Параметр сессии, а не константа.
- **Берём:** per-tick checksum (digest) для ловли десинка на раннем тике,
  а не «когда разошлась картинка». Формат digest фиксируем в §4.3.
- **Берём:** требование «сеть приходит пачками ввода по тикам, симуляция
  тикает независимо» — то же разделение, что L0 (§4.2).
- **Избегаем:** допущения «состояние маленькое и сериализуется бесплатно».
  Мир ornis (ECS + ресурсы + физика) большой; снапшот всего мира —
  отдельная задача со своим форматом и бюджетом (§5, порядок срезов).

### 1.5. Amethyst — ИЗБЕГАЕМ как анти-паттерн процесса

Что известно: Amethyst — открытый ECS-движок на Rust; разработка ушла
в бесконечный рерайт архитектуры вместо стабилизации релизов, проект
фактически заглох как игровой движок.

- **Берём (единственное):** ECS-организацию логики и data-driven подход —
  у ornis это уже есть (`crates/core`, `Schedule`, `ComponentRegistry`).
- **Избегаем:** «бесконечный рерайт вместо релизов». Прямое следствие для срезов:
  каждый срез L0/L1/L2 — независимо мержимый, со своим гейтом (§6),
  без перепроектирования ядра ради сети. Сеть адаптируется к `Engine`/`Schedule`,
  а не наоборот.
- **Избегаем:** расширение скоупа v1 (MMO-репликация, RPC, WebRTC) —
  см. «вне скоупа» в `PLAN.md` §l и §4.1.

### 1.6. Godot — КОНТРАСТ, вне скоупа v1

Что известно (Godot 4: авторитет узлов, `MultiplayerSynchronizer` для
репликации свойств, RPC-вызовы, server/client authority):

- **Понимаем как контраст:** модель Godot — репликация состояния
  (свойства узлов синхронизируются хостом) + RPC для событий.
  Это удобно для кооператива с толерантностью к расхождениям,
  но требует доверия к состоянию и не даёт бит-детерминизма.
- **В v1 не берём:** ни репликацию состояния, ни RPC. Причины:
  1) без детерминированного фундамента (он ещё строится: G8 не начат)
     репликация скрыла бы десинки вместо их ловли;
  2) физика ornis (Sequential Impulse, спящие тела, warm-start) не переживёт
     наложение чужого состояния без отката — нужен именно input-only + rollback;
  3) скоуп v1 — малые сессии lockstep/rollback (`PLAN.md` §l).
- **Возможно позже:** RPC-подобные команды лобби/мета-уровня (старт, пауза)
  поверх того же транспорта — но это уже за пределами v1.

### 1.7. Экосистема Bevy: renet, lightyear (naia, matchbox) — БЕРЁМ разделение слоёв

Что известно из открытых проектов:

- **renet** — тонкий транспортный слой (над UDP/QUIC-подобными каналами):
  надёжные/ненадёжные каналы, порядок не навязывает симуляции.
- **lightyear** — полнофункциональный netcode поверх: тик, предсказание,
  rollback, репликация, интересах к тику сервера.
- **naia / matchbox** — альтернативные транспорты (включая WebRTC/matchmaking
  для веба); подтверждают тезис «транспортов много, симуляция одна».

Выводы для ornis:

- **Берём:** жёсткое разделение «транспорт vs симуляция». В `crates/net`
  транспорт — трейт (§4.6), симуляция знает только `Tick` + ввод.
  Ошибка «смешение транспорта и симуляции» из `PLAN.md` тем самым
  закрывается на уровне типов.
- **Берём:** явный сетевой тик, независимый от рендер-кадра. У нас уже есть
  `FixedTime`/`Tick` (§2.1) — сеть маппится на него, а не на wall-clock.
- **Берём:** идею каналов с разной надёжностью (ввод — надёжно и по порядку
  номеров тиков; digest — можно ненадёжно/агрегатом) при выборе QUIC-каналов (§4.7).
- **Избегаем:** копирования lightyear целиком (репликация, интерес-менеджмент,
  серверный авторитет) — это вне скоупа v1. Берём только архитектурный приём,
  не фичи.
- **Избегаем:** привязки к одному транспорту: QUIC нативно в v1, wasm-вариант
  отдельно (§4.7), смена — заменой имплементации трейта.

### 1.8. Критические ошибки из `PLAN.md` — разбор каждой

`PLAN.md` §l перечисляет четыре ошибки. Для каждой: в чём суть и чем дизайн закрывает.

1. **Полу-состояния.**
   Суть: применение части сетевого обновления (половина ввода тика,
   половина снапшота) с продолжением симуляции «как-нибудь».
   Закрытие: ввод тика применяется атомарно — либо полный набор вводов
   всех пиров на тик, либо предсказание с последующим откатом (L1).
   Инвариант фиксируется тестом: тик никогда не видит «половину» `InputBundle`.
   Снапшот — версионированный целиком (`WorldSnapshot` + версия формата),
   частичный restore запрещён типом (restore возвращает `Result`, ошибка —
   десинк, а не продолжение).

2. **Смешение транспорта и симуляции.**
   Суть: сокеты, ретраи и таймауты внутри систем симуляции; тик зависит
   от состояния сети.
   Закрытие: `crates/net` делится на `Transport` (байты, тики не знает)
   и адаптер доставки (маппит arrivals в `Tick`, работает в L0 на границе
   кадра). Системы симуляции видят только ресурсы ввода на текущий `Tick`.
   Зависимости: `crates/net` зависит от `core`/`input`, но не наоборот.

3. **Wall-clock в тике.**
   Суть: `Instant::now()` или дельта кадра внутри детерминированного пути —
   пиры расходятся негарантированно.
   Закрытие: тик продвигается только на `FixedTime` (1/60 с), ввод
   привязан к `Tick(u64)`. `runner` (`crates/runner/src/lib.rs`)
   подаёт реальное время кадра только на границу variable-rate кадра,
   внутрь fixed-пути wall-clock не проникает. L0 явно отвязывает тик
   от wall-clock: arrivals ждут своего тика, а не «текущего момента».
   Гейт: тест «два прогона с разным wall-расписанием arrivals дают
   одинаковый digest-лог».

4. **Состояние вместо инпутов на проводе.**
   Суть: пересылка позиций/скоростей и наложение их на мир — скрытые
   десинки, читерство, отсутствие повтора.
   Закрытие: на проводе в v1 только ввод (`InputBundle` по тикам) + digest
   для проверки. Состояние по сети не ходит вообще (кроме bootstrap-сида
   сцены, который не является «состоянием симуляции», а её начальными
   условиями). L2-запись = тот же формат, что и провод: файл сессии
   можно скормить replay без сети.

## 2. Что уже есть в ornis (с путями к файлам)

### 2.1. Фиксированный шаг и тик

- `FixedTime` (1/60 с, поле `tick: u64`): `crates/core/src/engine.rs`
  (константа `DEFAULT_FIXED_DELTA_SECONDS = 1.0 / 60.0`, структура `FixedTime`,
  аккумулятор с капой `DEFAULT_MAX_FIXED_STEPS_PER_FRAME = 8`, сброс избытка
  вместо спирали догона).
- Тип `Tick(u64)` (newtype, сериализуется как число):
  `crates/core/src/typestate.rs` (рядом `Seconds`, `Frame`, `FixedSteps`).
- Физика на 60 Гц поверх того же fixed-пути:
  `crates/app/src/physics_runtime.rs` (домен физики шагается выбранным
  fixed-апдейтом; порядок sync-in → step → sync-out; в тестах кадра
  используется `engine.run_frame(1.0 / 60.0)`).

Вывод для дизайна: сетевой тик = `Tick` из `FixedTime`. Отдельного
«сетевого времени» не вводим.

### 2.2. Strong Confluence (детерминизм)

- Планировщик: `crates/core/src/schedule.rs`.
- Тесты: `crates/core/tests/confluence_tests.rs` (1-vs-32 паритет).
- Ночной гейт: `.github/workflows/determinism-nightly.yml`
  (долгие `#[ignore]`-тесты, регенераторы исключены через `--skip`,
  `known_limit_*` исключены — пинят лимиты солвера и падают ожидаемо).

Вывод: фундамент детерминизма уже есть и держится ночью. Rollback
обходится без него бессмысленным — предусловие L1: confluence зелёный.

### 2.3. Роли, мутации, реестр

- Роли `Authoritative` / `Replica` (phantom-параметры, default — Authoritative):
  `crates/core/src/typestate.rs`; использование — `crates/app/src/game_world.rs`
  (`GameWorld<Role>`, `ReplicaGameWorld = GameWorld<Replica>`; реплика
  наполняется из сериализованных снапшотов, раскладка мира та же).
- `MutationBus` (продьюсеры, `drain()`, `ticks()`, `MutationTick`, `MutationPlugin`):
  `crates/core/src/mutation.rs`.
- `ComponentRegistry` (имена, поля, `RegisterComponent`, сериализация компонентов):
  `crates/core/src/registry.rs`.

Вывод: роли уже различают «кто мутирует» на уровне типов — сеть их
переиспользует (авторитет симуляции vs ввод пиров), а не вводит свои.
`MutationBus.drain()` — естественная точка, куда L0 кладёт сетевой ввод
на границе тика. Реестр — основа будущего сериализуемого `Entity` (§4.6).

### 2.4. `WorldSnapshot` физики

- Формат: `crates/physics/src/snapshot.rs` (`WorldSnapshot`, `BodySnapshot`,
  `JointSnapshot`, события, warm-пары; `to_ron`/`from_ron`,
  `instantiate_si()`).
- Тест: `crates/physics/tests/world_snapshot.rs`.
- Ограничение сейчас: поддерживается только Sequential Impulse в режиме
  Single (`RoutingKind::Single`); остальное — `SnapshotError::Unsupported`,
  а не молчаливая потеря (`crates/physics/src/snapshot.rs`, строки про
  `Unsupported`).

Вывод: снапшот физики — готовый кусок L1, но только для SI-Single.
Границы сетевых сцен (§4.5) отсюда и следуют. Полный снапшот мира
(ECS + ресурсы + физика) — отдельная работа (§5: порядок срезов).

### 2.5. Ввод и хук «networked input»

- Крейт ввода: `crates/input` — `InputState::apply_snapshot()` wholesale-замена
  (`crates/input/src/state.rs`): продьюсеры пишут сырые коды, потребители
  читают через `InputMap`/`KeyCode` (`crates/input/src/lib.rs`, `map.rs`, `keys.rs`).
  Провод уже стабилен: `pressed_keys: Vec<u32>`, `pressed_mouse_buttons: Vec<u8>`
  по WS / `POST /api/input`.
- Пустой хук: `crates/gameplay/src/lib.rs` (около строки 414) — комментарий
  «намерение, пришедшее после fixed-фазы (например networked input), можно
  подмешать без двойного учёта»; сейчас residual нулевой, fixed-путь авторитетен.

Вывод: точка входа сетевого ввода известна заранее — L0 пишет в неё
на границе тика, а не «когда пришёл пакет».

### 2.6. `runner` и wall-clock

- `crates/runner/src/lib.rs`: хранит `last_frame: Instant`, обновляет его
  на границе кадра (`Instant::now()`).

Вывод: wall-clock живёт только на variable-rate границе. Дизайн запрещает
протаскивать его внутрь fixed-пути (см. ошибку №3 в §1.8).

### 2.7. `Entity` без serde и сетевого ID

- `crates/core/src/entity.rs`: `EntityId(u32)` + `Generation(u32)` + аллокатор
  с рециклом; `serde`-производных на `Entity` нет (grep по `serde` в файле пуст).

Вывод: для сети нужен сериализуемый сетевой ID и детерминированная выдача
(§4.6). Сейчас спавн вне сети порядок не гарантирует.

### 2.8. Только текстовая сериализация

- В `crates/core` — `serde_json`; снапшоты физики — RON
  (`WorldSnapshot::to_ron`/`from_ron`, `crates/physics/src/snapshot.rs`).
- Бинарного wire-формата нет.

Вывод: v1-проводу нужен компактный бинарный кодек (bincode/postcard-подобный,
решение — за L0-срезом, здесь фиксируем требование: детерминированный,
версионированный, без JSON на горячем пути).

### 2.9. Снапшоты детерминизма и G8

- Канонические снапшоты отдельные: `crates/physics/tests/data/`
  (`determinism_snapshot.x86_64.hex`, `determinism_snapshot.aarch64.hex`,
  плюс `avbd_snapshot.hex`).
- G8 (детерминизм CPU+GPU) не начат; GPU-путь (`WgpuContactSolver` /
  `GpuSequentialImpulse`, фича `gpu`) не бит-идентичен CPU по построению.

Вывод: в v1 пиры обязаны быть на одной архитектуре (§4.5); кросс-платформа
и G8-сцены — вне скоупа v1.

### 2.10. Сетевой код редактора — не основа мультиплеера

- `crates/editor-backend/src/remote.rs`: нативный loopback-транспорт —
  `TcpListener` на `127.0.0.1:{port}`, `RemoteEditor::start/stop`,
  loopback-only hardening (проверки `Host`/`Origin`, лимит тела).
- `crates/editor-backend/src/ipc.rs`: IPC того же loopback-контура редактора.

Почему не основа:

1. Это транспорт «редактор ↔ локальная игра» (команды UI, снапшоты сцены),
   а не «пир ↔ пир» (ввод по тикам, digest, откат).
2. Привязка к `127.0.0.1` и HTTP/WS-семантика — не игровой провод
   (нет тиков, каналов надёжности, QUIC).
3. Переиспользование создало бы ту самую ошибку «смешение транспорта
   и симуляции». Единственное, что можно позаимствовать, — практику
   loopback-тестов (in-process транспорт для тестов `crates/net`, §4.6).

## 3. Модель v1

- **Сессии:** малые (2–4 пира, P2P полносвязно или через релей; выделенного
  симуляционного сервера в v1 нет).
- **Симуляция:** lockstep с предсказанием и rollback (по GGPO-скелету, §1.4).
- **На проводе — только ввод:** на каждый `Tick` каждый пир публикует свой
  `InputBundle`. Состояние не пересылается.
- **Без репликации состояния:** `ReplicaGameWorld` из `game_world.rs`
  остаётся браузерным вьюпортом, а не сетевой репликой.
- **Предусловие:** Strong Confluence зелёный + сетевые сцены в границах §4.5.
  Без детерминизма rollback невозможен (зафиксировано в `PLAN.md` §l).

## 4. Дизайн по уровням

### 4.1. L0 — delivery model (граница ввода)

Правила доставки — инварианты, а не рекомендации:

1. Сетевые arrivals (ввод пиров) попадают в симуляцию **раз в тик**,
   **в начале кадра** (перед fixed-системами), в **порядке прибытия**,
   и **записываются** в локальный лог тика.
2. Тик **отвязан от wall-clock**: arrivals ждут своего `Tick`, тик не ждёт
   wall-момента. Опоздавший ввод → предсказание + пометка для L1-отката.
3. Хранилище: `Tick → InputBundle` (полный набор вводов всех пиров на тик;
   отсутствующий ввод помечен `predicted`).
4. Реплей идёт **без сети**: лог тиков + сид + версия = повтор прогона
   (мост к L2).
5. Атомарность тика: система видит либо полный `InputBundle`, либо
   предсказанный с флагом; «половин» не бывает (ошибка №1, §1.8).

Место в schedule: адаптер L0 выполняется на границе fixed-кадра
(до fixed-систем, после `MutationBus::drain()`-точки — ввод становится
частью мутаций тика). Системы симуляции читают ввод как ресурс текущего
`Tick` и про сеть не знают.

### 4.2. L1 — rollback (снапшот, digest, десинк)

Состав:

1. **Снапшот всего мира:** ECS (компоненты через `ComponentRegistry` +
   сериализуемый `Entity`, §4.6) + ресурсы (`FixedTime`/`Tick`, сид RNG,
   счётчики спавна) + физика (`WorldSnapshot`, сейчас только SI-Single).
   Формат версионирован; restore целиком или никак (`Result`, не полу-состояние).
2. **Restore и пересимуляция:** по GGPO-скелету (§1.4) —
   `save(tick) / load(tick) / advance(tick, inputs)`. Окно хранения —
   параметр сессии (по умолчанию несколько секунд тиков, точное число —
   за L1-срезом по замерам памяти снапшота).
3. **Per-tick digest:** хешируем на каждый тик:
   - номер тика + версию формата;
   - канонический ввод тика (после разрешения предсказаний);
   - позиции/ориентации тел, линейные/угловые скорости (квантованные
     к каноническому представлению — сырые `f32`-биты хешировать нельзя
     из-за `-0.0`/NaN; канонизация — за L1-срезом);
   - счётчик живых сущностей + хеш таблицы ID;
   - RNG-состояние.
   
   Хешёр: xxhash64 (быстрый, некриптографический; десинк-детект —
   не защита от читов). Пиры обмениваются digest на тик (агрегатом,
   не обязательно каждый тик отдельным пакетом).
4. **Реакция на десинк:** несовпадение digest → пометка тика,
   запрос полного снапшота у большинства/хоста (механизм согласования —
   за L1), пауза сессии с явным состоянием `Desynced(tick, digest_a, digest_b)`.
   Продолжение «как-нибудь» запрещено (ошибка №1).
   Античит в v1 не делаем (малые сессии, доверие пирам), только детект.

### 4.3. L2 — запись и replay

Формат записи сессии (файл `.ornis-rec`, версия в заголовке):

```
header: magic + format_version + engine_version + scene_id + seed + tick_rate(60) + peer_ids + input_delay
frames: повтор для каждого тика: tick_no + per-peer InputBundle + digest
footer: final_digest + tick_count
```

- Кодировка v1: компактный бинарный кодек (не JSON/RON — они остаются
  для сцен и отладки, не для горячего пути).
- CLI: `record` (писать во время сессии) / `replay --verify`
  (прогнать без сети, сверить per-tick digest с записанными, nonzero-exit
  при расхождении). Образец UX — Balaur Recordings-панель (§1.2, недоступна —
  делаем по этому описанию).
- Запись включается всегда в сетевых сессиях (дешёво: только ввод),
  хранится кольцом/пофайлово — политику решает L2-срез.

### 4.4. Границы v1 (что допустимо в сетевых сценах)

1. **Солверы/режимы:** только Sequential Impulse + `RoutingKind::Single`
   (единственное, что покрывает `WorldSnapshot`, §2.4). XPBD, AVBD, GPU-пути,
   multi-island параллельный солвер — вне сетевых сцен до покрытия снапшотом.
   Нарушение — ошибка сцены на загрузке, а не рантайм-десинк.
2. **CPU-only:** GPU-солверы не бит-идентичны CPU → в сетевых сценах запрещены.
   G8 (детерминизм CPU+GPU) не начат (§2.9) и является предусловием для
   ослабления этого правила, не частью v1.
3. **Одна архитектура у пиров:** x86_64-пиры играют с x86_64, aarch64 с aarch64
   (канонические снапшоты разные, §2.9). Кросс-арх — будущая работа
   (канонизация float/хлебные крошки — за пределами v1).
4. **Фиксированный tick rate 60 Гц**, `tick: u64` с нуля сессии.
   Сцены с другим шагом — вне v1.

### 4.5. Новый крейт `crates/net`

Публичная поверхность (имена рабочие, финализирует L0-срез):

```rust
// Транспорт ничего не знает про тики — только байты и пиры.
pub trait Transport: Send + Sync {
    fn send(&mut self, peer: PeerId, channel: Channel, bytes: &[u8]);
    fn recv(&mut self) -> Vec<Datagram>; // arrivals с прошлой границы
    fn peers(&self) -> Vec<PeerId>;
}

pub struct LoopbackTransport; // in-process, для тестов без сокетов

pub struct PeerId(pub u64);
pub enum Channel { ReliableInputs, UnreliableDigests }

#[derive(Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
pub struct Tick(pub u64); // реэкспорт/алиас core::Tick — решает L0,
                          // дубля не будет

pub struct InputBundle;   // ввод всех пиров на тик + бит predicted
pub struct SessionConfig { pub input_delay_ticks: u32, pub snapshot_window: u32, ... }

pub struct NetAdapter;    // L0: arrivals → Tick-лог на границе кадра
pub struct Rollback;      // L1: save/load/advance + digest-сравнение
pub struct Recorder;      // L2: record / replay --verify
```

- Место в schedule: `NetAdapter` — на границе fixed-кадра (до fixed-систем);
  `Rollback` — вокруг fixed-прогона (откат → пересимуляция → продолжение).
- Зависимости: `crates/net` зависит от `ornis-core`, `ornis-input`,
  `ornis-physics` (снапшот). Обратных зависимостей нет
  (симуляция про сеть не знает — закрытие ошибки №2).

### 4.6. Сериализуемый `Entity` и детерминированная выдача ID

Проблема (§2.7): `Entity = EntityId + Generation`, без serde и без
стабильного сетевого значения; порядок спавна детерминированности не даёт.

Решение v1:

1. Сетевой ID: `NetEntityId(u64)` — монотонный счётчик сессии,
   выдаётся авторитетом спавна детерминированно (порядок спавнов —
   функция тика и ввода, не wall-порядка). Маппинг `NetEntityId ↔ Entity`
   хранится в ресурсе мира и входит в снапшот (иначе restore сломает ссылки).
2. `Entity` получает serde-форму (пара `(slot, generation)`), но по проводу
   ходят только `NetEntityId` — локальные слоты аллокатора не утекают в сеть.
3. Детерминированная выдача: спавны, вызванные симуляцией, выполняются
   в каноническом порядке (сортировка по `NetEntityId` при итерировании
   в сетевых сценах); удалённые ID не переиспользуются внутри сессии
   (поколения — только для локального аллокатора).

### 4.7. Транспорт: QUIC (quinn) нативно, вариант для wasm

- **v1 нативно:** QUIC через `quinn`. Причины: один порт, TLS из коробки,
  мультиплексирование (ввод — надёжный ordered-поток/канал, digest —
  ненадёжные датаграмы), миграция соединений, raw UDP отдельно не нужен
  (покрывается QUIC-датаграмами — как уже зафиксировано в `PLAN.md` §l).
- **wasm:** QUIC в браузере недоступен → WebTransport-клиент поверх того же
  `Transport`-трейта (тот же `InputBundle`-поток, другой драйвер байтов).
  WebTransport-бэкенд — за пределами v1 (`PLAN.md` §l), но трейт это
  предусматривает заранее, рефакторинга ядра не потребуется.
- **В v1 не делаем:** WebRTC, raw UDP, MMO-репликацию, серверный авторитет.

## 5. Порядок срезов (с обоснованием)

Рассмотренный вариант: **сначала L2 (запись + replay с проверкой хеша),
потом снапшот всего мира, потом L0, потом L1**.

**Вердикт: согласен, с одной поправкой — снапшот идёт внутри L2-подготовки,
а не отдельным срезом.** Итоговый порядок:

1. **L2-recording (запись + `replay --verify`) — первым.**
   Причина: replay проверяет детерминизм всего мира без сети.
   Локальная запись «ввод + сид» и прогон с per-tick digest — самый дешёвый
   способ доказать, что мир вообще способен к rollback-будущему.
   Если replay локально расходится — проблема в детерминизме, и сеть её
   только замаскирует. Плюс: с первого среза есть артефакт для баг-репортов.
2. **Снапшот всего мира (ECS + ресурсы + физика) — вторым.**
   Причина: это самая рискованная техническая часть (размер, канонизация
   float, restore без полу-состояний). Делать её до L0 — значит прийти
   к сетевому коду с уже готовым save/load. Поправка: оформляем не отдельным
   срезом, а частью L2→L1 (критерий: `save → load → advance` даёт тот же
   digest, что непрерывный прогон — без единого сокета).
3. **L0 (delivery model) — третьим.**
   Причина: когда запись/replay и снапшот готовы, L0 — «тонкая» работа:
   arrivals в Tick-лог на границе кадра + `Transport`-трейт + loopback.
   Риск минимален, тестируется детерминированно (лог arrivals → replay).
4. **L1 (rollback) — последним.**
   Причина: L1 — композиция готовых частей (снапшот + Tick-лог + digest).
   Нового механизма почти нет, только политика (окно, предсказание,
   реакция на десинк). Самый сложный в отладке — поэтому идёт тогда,
   когда всё под ним уже проверено.

Альтернатива «L0 первым» отвергнута: сеть без replay-верификации
и без save/load даёт немые десинки, которые нечем ловить и нечем
воспроизводить. Порядок «верификация → состояние → доставка → откат»
каждый следующий срез строит на проверяемом предыдущем.

## 6. Задачи, критерии, тесты и гейты по срезам

Каждый срез — независимо мержимая issue со своим гейтом
(урок Amethyst, §1.5: без рерайтов ядра).

### 6.1. Срез L2 — запись и replay (первый)

Задачи (файлы):

1. Формат `.ornis-rec` (§4.3): header/frames/footer, версия, бинарный кодек.
   Новый модуль записи (кандидат: `crates/net/src/record.rs`, крейт `crates/net`
   создаётся этим срезом в минимальном виде — только запись, без транспорта).
2. Сериализация `InputBundle` (канонический ввод тика; опора —
   `crates/input/src/state.rs::apply_snapshot`, `crates/input/src/map.rs`).
3. CLI `record` / `replay --verify` (место CLI — за срезом; кандидат —
   расширение существующего бинаря runner/xtask, без нового транспорта).
4. Per-tick digest v0 (состав §4.2 п.3; хешёр xxhash64; канонизация float —
   минимум, достаточный для same-arch повтора).

Критерии готовности:

- Запись 10-минутной сессии открывается replay без сети и даёт
  побитово тот же digest-лог.
- `replay --verify` возвращает nonzero-exit при подмене одного байта ввода.
- Формат версионирован: `from_*` отказывается читать будущую версию с понятной
  ошибкой (не молчаливым дрейфом).

Тесты и гейт:

- Юнит: round-trip кодека (пустой ввод, полный ввод, граничные тики).
- Интеграционный: «записал → проиграл → digest совпал» на фиксированной сцене.
- Негативный: подмена ввода/версии → явная ошибка.
- Гейт: `cargo test -p ornis-net` + clippy/fmt по правилам `AGENTS.md`;
  детерминизм-гейт (`determinism-nightly`) остаётся зелёным.

### 6.2. Срез «снапшот всего мира» (второй)

Задачи (файлы):

1. Расширение `WorldSnapshot` (`crates/physics/src/snapshot.rs`) до границ §4.4
   или фиксация отказа для остального (`Unsupported`, как сейчас).
2. Снапшот ECS: компоненты через `ComponentRegistry`
   (`crates/core/src/registry.rs`) + сериализуемый `Entity`
   (`crates/core/src/entity.rs`) + маппинг `NetEntityId` (§4.6).
3. Снапшот ресурсов: `FixedTime`/`Tick` (`crates/core/src/engine.rs`,
   `crates/core/src/typestate.rs`), сид RNG, счётчики спавна.
4. `save(tick) / load(tick)` с атомарностью (целиком или `Err`, §1.8 п.1).

Критерии готовности:

- `save → N тиков → load → те же N тиков` даёт тот же digest, что непрерывный
  прогон (без сети).
- Неподдерживаемая сцена (GPU-солвер, не-SI режим) отказывается загружаться
  в «сетевой режим» с понятной ошибкой, а не десинком в рантайме.
- Размер снапшота и время save/load замерены и записаны в док срезa
  (бюджет окна L1 считается из них).

Тесты и гейт:

- Юнит: round-trip каждого компонента снапшота.
- Интеграционный: save/load-эквивалентность на SI-Single сценах из
  `crates/physics/tests/world_snapshot.rs` + минимум одна ECS-сцена.
- Гейт: те же, что L2, плюс отсутствие регресса `world_snapshot`-тестов.

### 6.3. Срез L0 — delivery model (третий)

Задачи (файлы):

1. Крейт `crates/net`: `Transport`-трейт + `LoopbackTransport`
   (только loopback, без сокетов в этом срезе).
2. `NetAdapter`: arrivals → `Tick → InputBundle` на границе fixed-кадра
   (точка входа — хук из `crates/gameplay/src/lib.rs`, ввод — через
   `InputState::apply_snapshot` в `crates/input/src/state.rs`).
3. Tick-лог + запись (связка с L2-рекордером: лог пишется в формате `.ornis-rec`).
4. Отвязка от wall-clock: тик не зависит от расписания arrivals
   (тест с двумя расписаниями — один digest-лог).

Критерии готовности:

- Два пира на loopback-транспорте с искусственной задержкой/перемешиванием
  arrivals дают тот же digest-лог, что локальный прогон.
- Тик никогда не видит частичный `InputBundle` (инвариант покрыт тестом).
- `runner` (`crates/runner/src/lib.rs`) не проникает wall-clock внутрь
  fixed-пути (ревью + тест с разными wall-расписаниями).

Тесты и гейт:

- Детерминированный симулятор сети (задержка, дубли, переупорядочивание)
  поверх `LoopbackTransport`.
- Паритет «сеть-loopback vs локально» по digest.
- Гейт: `cargo test -p ornis-net`, clippy/fmt; confluence зелёный.

### 6.4. Срез L1 — rollback (последний)

Задачи (файлы):

1. `Rollback`: `save/load/advance`, окно снапшотов (параметр сессии),
   предсказание опоздавшего ввода, пересимуляция
   (всё в `crates/net`, новый модуль поверх готовых save/load и Tick-лога).
2. Обмен digest (канал `UnreliableDigests`), сравнение, состояние
   `Desynced(tick, a, b)` + пауза сессии.
3. Параметр `input_delay_ticks` (`SessionConfig`) с дефолтом по замерам.
4. QUIC-транспорт (`quinn`) за этим же или следующим срезом —
   решение за issue L1 (loopback уже покрывает логику; сокеты — отдельно
   мержимая добавка без смены интерфейса).

Критерии готовности:

- Искусственная потеря/задержка ввода на loopback приводит к откату,
  а не к расхождению: digest-лог после пересимуляции совпадает с эталоном.
- Десинк (подмена digest) ловится на тике расхождения, сессия переходит
  в `Desynced` с указанием тика и обеих сумм.
- Окно отката покрывает 99-й перцентиль измеренной задержки тестовой сети
  (число фиксируется в issue по замерам, не «на глаз»).

Тесты и гейт:

- Хаос-тест: рандомизированные задержки/потери на loopback, сверка digest.
- Десинк-инжекция: подмена состояния одного пира → детект на ожидаемом тике.
- Нагрузочный: замер времени пересимуляции окна (бюджет кадра не превышен).
- Гейт: полный набор + ночной determinism зелёный; PR — draft до ревью Юры.

## 7. Риски и открытые вопросы для Юры

Риски:

1. **Размер снапшота мира.** Полный ECS+физика снапшот может оказаться
   слишком тяжёлым для окна в секунды тиков. Митигация: замер в срезе
   снапшота (§6.2) до фиксации окна; при необходимости — дельта-снапшоты
   или урезанный набор компонентов (но это уже редизайн, отдельной issue).
2. **Канонизация float для digest.** Сырые биты `f32` хешировать нельзя
   (`-0.0`, NaN). Нужна каноническая форма — объём работы виден только
   при реализации. Митигация: v0 — same-arch + простая канонизация
   (нормализация нулей, запрет NaN в хешируемом состоянии).
3. **Кросс-архитектура.** Канонические снапшоты разные (x86_64 vs aarch64).
   v1 — same-arch only (§4.4). Кросс-платформа — отдельная большая работа.
4. **QUIC-зависимость (`quinn`).** Новая тяжёлая зависимость с транзитивами;
   гейт `cargo outdated --exit-code 1` (см. `AGENTS.md`) может покраснеть.
   Митигация: транспорт за трейтом — сокеты подключаются последним
   независимым шагом; loopback покрывает всю логику без `quinn`.
5. **Скоуп-крип.** Соблазн добавить репликацию/RPC «по пути». Запрет уже
   зафиксирован (`PLAN.md` §l + §1.5 + §4.1): такие предложения — отдельными
   issue за пределами v1.

Открытые вопросы (ждём решения Юры):

1. Доступ к Balaur (`docs/PLAN-networking.md`, rollback-модуль,
   Recordings-панель): дать доступ или подтвердить, что проектируем без них?
2. Дефолт `input_delay_ticks` и размер окна отката — фиксируем после замеров
   (§6.4) или нужен целевой бюджет (например «окно = 120 тиков») уже сейчас?
3. QUIC в L1-срезе или отдельным срезом после L1 на loopback?
4. Формат `.ornis-rec` — отдельный файл-спека в `docs/` или достаточно §4.3?
5. Нужен ли в v1 релей для пиров за NAT, или достаточно прямого соединения
   (тестовая эксплуатация в одной сети)?
6. Подтвердить same-arch ограничение v1 (x86_64↔x86_64, aarch64↔aarch64)
   как приемлемое для первых сессий.
