## 2. Ядро ECS

### 2.1 [P0] `ZipIter`: `?` в `next()` обрывает итерацию целиком; `size_hint` заявляет exact

`crates/core/src/component_store.rs:255,260` — sparse-lookup через
`.copied()?` внутри `Iterator::next`: если инвариант «бит взведён ⇒
страница существует» хотя бы раз сломается, итератор **молча вернёт
`None` и оборвёт обход** вместо пропуска элемента (ср. `iter_without`,
строка 190, где тот же lookup корректно обёрнут в `filter_map` → skip).
`size_hint` (строка 273) возвращает `(remaining, Some(remaining))` —
точность опирается на тот же негласный инвариант.

**Требование исправления:** skip-семантика (как `iter_without`) +
`size_hint = (0, Some(remaining))`, либо `debug_assert` инварианта с
комментарием, почему он непреложен.

> ✅ **Закрыто 2026-08-22**: `next()` делегирует в `ZipIter::lookup()`,
> где `?` означает skip одного id, а не обрыв обхода; `size_hint` —
> честный `(0, Some(remaining))`. Регрессии: юнит-тест
> `zip_iter_skips_generation_mismatch` (recycled id, разные поколения в
> двух сторах; skip не прерывает обход) и модельный proptest
> `zip_matches_model` (zip двух случайных сторов против двух HashMap).

### 2.2 [P0] Тавтологические (мёртвые) проверки generation

`component_store.rs:191-194` (`iter_without`) и `:256-258`, `:261-263`
(`ZipIter::next`): `entity` — копия `self.entities[dense_idx]`, а её
`generation()` сравнивается с `self.entities[dense_idx].generation()` —
условие **всегда ложно**. Обрезки рефакторинга в самом горячем коде ядра;
маскируют реальную семантику проверок на протухший handle (которая в
`get`/`remove` сделана правильно — сравнение с generation **хендла**).

**Требование:** удалить мёртвые ветки или восстановить осмысленную
проверку; добавить proptest-регрессию на zip-итерацию с переработанными
(recycled) сущностями.

> ✅ **Закрыто 2026-08-22**: тавтологии удалены из `iter_without` и
> `ZipIter`; осмысленная проверка (generation стора A против стора B на
> одном слоте — защита от recycled-slab рассинхрона) сохранена в
> `ZipIter::lookup()` и покрыта тестами из 2.1.

### 2.3 [P1] `for_each_entity!` с 3+ лентами паникует на частичном владении

`crates/macros/src/for_each_entity.rs:139` — кодген собирает сущности из
`iter_zip` только **первых двух** лент, а компоненты остальных достаёт
через `get(entity).unwrap()` (`:146-157`): сущность с Position+Velocity,
но без Force уронит сгенерированный цикл паникой, хотя семантика запроса
подразумевает пересечение **всех** объявленных лент. Среди пользователей
макроса трёхленточные вызовы есть только в `confluence_tests.rs`
(`:235,279,511,555`), где каждая сущность всегда получает полный набор
компонентов, — паникующий путь ничем не покрыт. Найдено при проверке
контрактов `ZipIter` (2.1).

**Требование:** пересекать все ленты (цепочка `filter(contains)` по
лишним лентам или общий битсет) + регрессионный тест с частичным
владением компонентами.

> ✅ **Закрыто 2026-08-22**: кодген пересекает все ленты — zip первых
> двух + `filter(contains)` по лентам 3..N (`contains` тоже сверяет
> generation, семантика идентична). Регрессия:
> `for_each_entity_macro_three_lanes_skips_partial_ownership`
> (`macro_integration.rs`) — сущность без Force не посещается, её
> данные не тронуты; на старом кодегене тест падал паникой unwrap.

## 3. Планировщик (`crates/core/src/schedule.rs`)

### 3.0 Контекст оценки

Алгоритм уровней корректен по построению (рёбра только i→j при i<j ⇒ DAG;
`BackwardEdge` отвергается при добавлении), семантика конфликтов
(RaW/WaW/WaR, read-read свободно) верна и пинится дифференциальным
тестом `bitset_plan_matches_reference_model` к Vec-эталону. Проблемы —
не в алгоритме, а в контрактах и интеграции.

### 3.1 [P1] У `Schedule` ноль пользователей вне собственных тестов

`Schedule::new` не вызывается нигде в движке (`src/`, `crates/*` — grep:
только реэкспорт в `crates/core/src/lib.rs:32`); рендер-графу нужен лишь
`compute_levels` (`crates/render/src/render_graph.rs:224`); главные
параллельные нагрузки (`smart_pipeline`, `for_each_entity`) исполняются
мимо шедулера. Сам PLAN (раздел «g») относит «кадр через верхний
`Schedule`» к будущей работе. Статус «Unified Scheduler ✅» в README —
это ✅ кода-фундамента, не интеграции.

### 3.2 [P0] Контракт детерминизма недоопределён: Mutex ≠ конруэнтность

Модульная документация (`schedule.rs:1-29`) обещает Strong Confluence
«при условии, что ресурсы используют внутреннюю изменяемость
(`Mutex`/атомики)». Внутренняя изменяемость даёт **безопасность памяти,
а не детерминизм**: две системы одного уровня, пишущие в один
`Mutex<Vec>`, получают недетерминированный порядок lock'ов → результат
различается между прогонами и с последовательным режимом. Собственный
тест `parallel_matches_sequential` вынужденно признаёт это — сортирует
события перед сравнением (`schedule.rs:716-717`).

**Требование:** зафиксировать в контракте: ресурсы, объявленные `reads`
и мутируемые изнутри, обязаны быть **коммутативными аккумуляторами**
(атомики с коммутативными операциями, append=мультимножество и т.п.);
мутируемые некоммутативно ресурсы обязаны объявляться `writes`.

> ✅ **Закрыто 2026-08-22**: модульная документация `schedule.rs`
> дополнена разделом «Контракт коммутативности» с формулировкой выше;
> абзац про Strong Confluence больше не обещает детерминизм «при условии
> Mutex», а ссылается на контракт.

### 3.3 [P2] Enforcement не покрывает системы с внутренним параллелизмом

Проверка объявленных доступов — TLS-стек (`ACCESS_FRAMES`,
`schedule.rs:252-255`), она действует только в потоке, вызвавшем
`system.run()`. Система, запустившая внутри себя `rayon` (а это ровно
то, что генерирует `#[smart_pipeline]` — главный паттерн движка),
исполняет дочерние задачи на других потоках с пустым стеком → доступ
не проверяется. Дополнительно: проверка по умолчанию debug-only
(`enforce_accesses: cfg!(debug_assertions)`, `schedule.rs:355`) — в
release нарушение становится тихой логической гонкой.

**Требование:** документировать ограничение; рассмотреть распространение
фрейма в rayon-задачи (`rayon::scope`/spawn с контекстом) или
обёртку-«capture» ресурсов до входа в параллельную секцию.

> ✅ **Закрыто 2026-08-23 (бэклог #7)**: распространение реализовано —
> `capture_access_frame` + `AccessFrameCapture::install`
> (`crates/core/src/schedule.rs`) переносят верхний TLS-кадр в дочерние
> потоки (RAII-откат при паниках; пустой снимок вне `run` — no-op, ноль
> аллокаций). `#[smart_pipeline]` генерирует захват+установку вокруг
> `par_iter`-тел в обеих ветвях — одна лента и zip двух
> (`crates/macros/src/smart_pipeline.rs`), главный паттерн движка покрыт
> автоматически; вложенные переписанные циклы наследуют кадр транзитивно.
> Регрессии: `undeclared_access_in_child_thread_panics_with_captured_frame`
> (`std::thread::scope` — детерминированно чужой поток, паника ребёнка
> докатывается авто-join'ом scope), positive-кейс own-write read
> `declared_access_in_child_thread_passes_with_captured_frame` и no-op
> `capture_outside_schedule_run_is_noop`. Задокументированный лимит
> оставлен осознанно (вторая часть требования §3.3): ручной
> `rayon`/`std`-параллелизм внутри системы **без** захвата вне проверки;
> проверка по умолчанию debug-only.

### 3.4 [P2] `access()` фиксируется снапшотом при регистрации

`add_system` кладёт `system.access()` в `accesses` один раз
(`schedule.rs:368-376`); динamический `access()` (зависящий от состояния
системы) молча рассинхронизируется с планом и с enforcement'ом.

**Требование:** документировать «доступы — статические данные» контракт
трейта `System`, либо переснимать снапшот перед каждым `run` (дорого,
не рекомендуется).

### 3.5 [P3] План клонируется на каждый `run`; enforcement клонирует доступы

`cached_levels` (`schedule.rs:470-483`) возвращает `levels.clone()`
из-под Mutex на каждый кадр; `AccessFrameGuard::push` (`schedule.rs:264-272`)
клонирует `reads`/`writes` на каждый запуск каждой системы. Рябь мелкая,
но это ровно тот кадровый путь, ради которого планировщик и кешируется.
Рядом рендер-граф отдаёт `&GraphLayout` без копирования — два разных
стиля кеша в одном проекте.

**Требование:** `Arc`-снимок плана (или `arc_swap`), предвычисленные
кадры enforcement по индексу системы вместо клонов.

### 3.6 [P1] Нет гранулярности до лент `SmartStore`

`SystemAccess` оперирует только TypeId синглтонов. Если положить
`SmartStore` в `Resources` одним ресурсом — все системы конфликтуют по
нему и сериализуются; если не класть — зависимости по компонентам
невидимы для планировщика (ручные `order_before`). Планировщик
**в принципе не умеет планировать главные системы движка** — циклы по
лента-м компонентов.

**Требование:** протокол доступов уровня лент (TypeId компонента),
совместимый с `SmartStore::read_lane/write_lane`; ключевая часть Фазы B/C
плана ниже.

> ✅ **Закрыто 2026-08-23 (бэклог #5)**: протокол лент реализован в
> `core::schedule` — `SystemAccess::reads_lane/writes_lane` по
> `TypeId` компонента (+`_id`-варианты для динамических фронтендов
> через реестр F0, `ComponentMeta::type_id`). Ресурсы и ленты —
> раздельные пространства имён ключей планировщика (ложных конфликтов
> «ресурс vs лента одного типа» нет). Принуждение — на границе
> `SmartStore::read_lane/write_lane`: чтение покрывается `reads_lane`
> или `writes_lane`, запись — строго `writes_lane`; cold- и lock-free
> ленты вне протокола (отдельные пространства имён). Критерий «система
> над двумя лентами в плане без ручных `order_before`» закрыт
> интеграционными тестами `crates/core/tests/schedule_lanes.rs`,
> включая LCG-дифференциальный против наивной модели конфликтов.

## 4. Рендер-граф

### 4.1 [P2] У пассов нет enforcement объявленных доступов

Инвариант «пассы, пишущие в один queue-backed буфер вне declared
accesses, обязаны попасть в разные уровни» существует только как
комментарий для авторов пассов (`crates/render/src/graph_frame.rs:97-105`).
Асимметрия: у систем enforcement есть (пусть и с оговорками 3.3), у
пассов — нет вообще. Ошибка автора пасса = недетерминированный/невалидный
кадр без диагностики.

**Требование:** debug-проверка при выдаче view по `ResourceId`
(пасс запрашивает ресурс вне declared reads/writes → паника с именем
пасса и ресурса).

> ✅ **Закрыто 2026-08-23 (бэклог #6)**: debug-проверка на границе выдачи
> view — `PassViews::view_of` (единая воронка для обоих фронтендов:
> типизированных систем `SystemViews` и императивных run-замыканий)
> вызывает `assert_pass_access_declared` (`render_graph.rs`); пасс,
> запросивший `ResourceId` вне своих declared reads/writes, паникует в
> debug с именем пасса и ресурса (индекс пасса и хендл тоже в сообщении).
> Только debug (`#[cfg(debug_assertions)]`): в release проверка
> скомпилирована в ноль. Регрессии: `sneaky_pass_undeclared_access_panics`
> и `declared_pass_access_passes_enforcement` (`render_graph.rs`),
> `pass_views_undeclared_view_panics_in_debug` (`graph_frame.rs` — путь
> через реальный `PassViews`, device-free). Лимит, симметричный §3.3:
> `queue.write_buffer` в renderer-uniforms не проходит через `view_of`, поэтому
> инвариант queue-backed буферов остаётся авторским контрактом (комментарий
> `GraphExecutor::execute_parallel` обновлён). Типизированный фронтенд имел
> частичный `debug_assert` в `SystemViews::get` (только `get::<R>()`,
> type-level множества) — проверка ground truth на уровне `ResourceId`
> поглощает его и закрывает императивный фронтенд.

### 4.2 [P1] Дублирование механики с `core::Schedule`

Независимые реализации одного и того же: семантика конфликтов
(`passes_conflict`, `render_graph.rs:229-240` vs `conflicts`,
`schedule.rs:196-199`); `order_before`/`try_order_before` + ошибка
`BackwardEdge` (`render_graph.rs:561-590` vs `schedule.rs:401-452` —
почти дословная копия); кеш плана со счётчиком (`layout_computations`,
`render_graph.rs:453,704` vs `level_computations`); дуальное
sequential/parallel исполнение + wasm32-близнец. Уже столкнулись имёнами
(`SystemAccess` переименован из-за render-`Access`).

**Требование:** Фаза A плана (раздел 7).

> ✅ **Закрыто 2026-08-23 (бэклог #4)**: механика переехала в крейт
> `crates/schedule` (`ornis-schedule`): `compute_levels`, обобщённый
> по ключу `K` битсет-план `bitset_level_plan`, единый `OrderError`
> (`UnknownNode`/`BackwardEdge`) с общими валидаторами рёбер
> (`resolve_named_edge`/`validate_indexed_edge`), кеш `PlanCache` с
> диагностикой, уровневый исполнитель `run_levels` (sequential / rayon /
> wasm-последовательность). `core::Schedule` и `RenderGraph` переведены
> на общий engine; `passes_conflict`, `GraphOrderError` и дубли
> валидации рёбер удалены; `ornis_core::compute_levels` — реэкспорт.
> Добивка 2026-08-23 (бэклог #19): антидрейф-канон — паритет-тест
> фронтендов (`crates/render/tests/scheduler_parity.rs` ломается при
> семантическом расхождении), нейминг унифицирован (`Schedule::levels()`),
> карта+глоссарий в `docs/rendering/unified-scheduler.md`, исполнитель
> записи пассов — на `run_levels`.

### 4.3 [P3] `levels()` пересчитывается без кеша и без битсетов

`GraphLayout::levels()` (`render_graph.rs:209-227`) на каждый вызов:
O(n²·E) с `Vec::contains` по рёбрам идоступам; битсет-проекции (как в
core) нет, в кеш `GraphLayout` уровни не входят. При ~10 пассах
незаметно, при сотнях — кадровая стоимость.

**Требование:** включить уровни (битсет-план) в кешируемый `GraphLayout`
— естественно закрывается Фазой A.

> ✅ **Закрыто 2026-08-23 (бэклог #4)**: уровни — поле
> `GraphLayout::levels` битсет-плана `ornis_schedule::bitset_level_plan`,
> вычисляются один раз в `compute_layout` и кешируются вместе с layout;
> аксессор клонирует готовый вектор.

## 6. Прочие пробелы

### 6.1 [P2] Физика
- `shapecast` — stub (`None`), при наличии метода в публичном трейте
  `PhysicsEngine`.
- «Плагинная точка» Rapier/Jolt: трейт есть, адаптеров нет — тезис о
  плагинности не проверен ни одной реализацией извне.

### 6.2 [P2] Редактор
- WASM-viewport рендерит **статичный** `scene.ron`, живой ECS-мир
  (`src/editor_world.rs`) на рендер не влияет: редактируется одно,
  отображается другое (план — дорожная карта README, пункт 4).
- Синхронизация polling'ом `/api/scene`+`/api/status` (1.5 с) вместо
  WebSocket — задержки и лишний трафик при live-редактировании.
- Команды редактора — ручной `match` по строкам с per-type методами
  (`src/editor_world.rs:272-310`): `"set_transform"`/`"set_material"`/
  `"rename_entity"` хардкодят конкретные типы; новый компонент движка
  становится редактируемым только после правки engine-side кода —
  инверсия «движок подстраивается под редактор». Заготовка
  универсального протокола существует, но не используется:
  `UiCommand::SetComponent { type_name, json_data }` (`src/ipc.rs:24-30`,
  зарезервирован, `#[allow(dead_code)]`). → закрывается решением D2 (§10).

## 7. План: унификация планировщика в отдельный крейт

Решение (согласовано в обсуждении): объединять **механику** планирования,
не семантику ресурсов. Полный мердж «пасс = система» (IDEAS §28) —
после появления у `Schedule` второго живого пользователя.

### Фаза A — выделить `crates/schedule` (engine-крейт)

Переносится механика: `compute_levels`, обобщённый битсет-план конфликтов,
явные рёбра с валидацией + единый `OrderError`/`BackwardEdge`, кеш плана
с диагностикой, уровневый исполнитель (sequential / rayon /
wasm-последовательность). Зависимости: `fixedbitset`, `rayon`. **Никаких
wgpu и ECS**: пул текстур, лайфтаймы, бюджет S4, `PassContext`/`Resources`
остаются в доменных крейтах.

```
        crates/schedule — узлы, доступы, рёбра, уровни, кеш, исполнители
           ▲                     (deps: fixedbitset, rayon)
   ┌───────┴────────┐
 ornis-core      ornis-render
 (Resources,     (пул/лайфтаймы/PassViews,
  SystemAccess)   PassBuilder как фронтенд)
```

Далее: `render_graph.rs` и `schedule.rs` переводятся на общий engine,
дубли (4.2) удаляются; уровни рендер-графа получают битсет-план и
включаются в кеш `GraphLayout` (закрывает 4.3).

**Статус 2026-08-23: выполнено** (бэклог #4). Крейт на месте, оба
фронтенда переведены, дубли удалены (`render_graph.rs` похудел:
`passes_conflict`/`GraphOrderError`/дубли валидации ушли), уровни
рендер-графа — битсет-план в кеше `GraphLayout`. Дифференциальный тест
живёт в `crates/schedule` (`bitset_plan_matches_reference_model`) и
гоняется против обоих потребителей: в core — одноимённый регрессионный
тест `Schedule`, в render — золотые разбиения `levels()` вплоть до
production-графа (`graph_frame`). Golden-тесты пула и pixel-probe'ы не
тронуты.

**Критерии выхода:** `cargo xtask quality` зелёный; дифференциальный
тест битсет-плана живёт в новом крейте и гоняется против обоих
потребителей; golden-тесты пула и pixel-probe'ы рендера без изменений;
`render_graph.rs` худеет (нет своих `order_before`/уровней).

## 10. Протокольные решения (2026-08-22)

Приняты в обсуждении аудита (скриптинг и связка движок↔редактор);
фаза 6 PLAN.md обновлена под D1. Общий фундамент обоих решений —
реестр компонентов (F0).

### F0. Реестр компонентов (reflection-lite, фундамент)

Реестр: имя ↔ `TypeId` ↔ type-erased операции — insert/get/remove
компонента в `SmartStore`, serde JSON в/из компонента; мономорфные
thunk'и генерируются макросом (свой макро-крейт уже есть). Границы
применимости:

- **только tooling-пути**: FFI/редактор/сериализация сцен; горячие
  циклы остаются типизированными (SoA-ленты, макросы) — граница как у
  Bevy (`bevy_reflect` для инструментов, типизированные квери для
  кадра);
- один реестр обслуживает D1 (скриптинг), D2 (редактор), гранулярность
  лент шедулера (§3.6) и generic-десериализацию сцен фазы 7.

### D1. Скриптинг — плагинный шов вместо «лесенки языков»

- `ScriptEngine` — третий плагинный трейт рядом с `PhysicsEngine` и
  `RenderBackend` (IDEAS, идея №6): ядро знает только трейт
  (load/call/batch/ hot reload), языки — адаптеры.
- Batch-контракт — **по хендлам, не по указателям**: сырые указатели
  на ячейки Sparse Set совместимы только с in-process FFI и ломают
  WASM-сценарий (sandbox); единый handle-based Batch API обслуживает
  оба мира.
- Порядок: первый адаптер — Rhai, за ним hot reload; Rune /
  Python(rustpython) / WASM-компоненты — отдельными адаптерами после
  проверки шва минимум двумя реализациями (правило трёх); WASM —
  исследовательский трек (языко-нейтральность + sandbox).

### D2. Редактор — внешний клиент реестрового протокола

- World-протокол v2: generic-команды через реестр (`SetComponent
  { type_name, json }` — заготовка уже есть, `src/ipc.rs:24-30`);
  per-type `cmd_set_transform`/`cmd_set_material` удаляются; новый
  компонент движка становится редактируемым без правок engine-side
  кода (модель bevy_remote/BRP). Редактор подстраивается под код
  движка, не наоборот.
- «Движок без редактора, как в Bevy»: крейты-библиотеки уже чисты;
  дополнительно remote-сервер в нативном режиме — за явным флагом, а
  не по умолчанию; редактор-сервер и фронтенд остаются dev-tool'ом,
  движку для работы не нужны.
