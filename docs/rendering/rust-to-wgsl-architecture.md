# Rust → WGSL: архитектура перехода

> **2026-10-17:** выбрано направление «staged-метапрограммирование»
> (§3.1) в варианте «скрытые generics» (§3.1.1), идеи Slang вынесены в
> §3.2, отклонены wasm-путь и rust-gpu как основной (§4); долгосрочный
> вариант «rust-gpu без nightly» через LLVM IR — §3.1.2, порядок и
> критерии спайков — §3.1.3.

Статус на 2026-09-10: 11 stage-entry пишутся на Rust через `#[stage]`
и собираются в WGSL.base. Свободных идентификаторов в entry нет;
остаток закрыт: `EPS`/`PI` генерируются из Rust-констант (`f32_lit` +
`decl!`, имя через `stringify!`), имена kernel-функций текут
идентификаторами (ноль строковых литералов в `render/`, пинится
`stage_calls_resolve`), вложенные бандлы — вторыми `Context<T>`
-параметрами (`consts.quad`, `maps.albedo_tex`).
`naga` — backend деклараций + финальный валидатор, не источник API.

## 1. Текущее состояние (факт, сверено с кодом)

```rust
#[stage(vertex)]
fn vs_main(
    vertex_index: super::VertexIndex,
    ctx: Context<super::QuadContext>,
) -> CompositeVertexOutput {
    CompositeVertexOutput {
        clip_position: ctx.quad[vertex_index],
        uv: ctx.uvs[vertex_index],
    }
}
```

- **Сигнатуры — чистый Rust:** builtin-индексы — newtypes
  (`VertexIndex`/`InstanceIndex`, маппинг по имени типа как у glam);
  ресурсы — bundle `ctx: Context<Bundle>` (обёртка, не атрибут; голая
  структура `input: VertexInput` остаётся настоящим WGSL-параметром);
  location'ы — на полях `WgslInterface`-структур, entry берут struct-input
  (`input.uv`, не голый `uv`); located-возвраты — типом
  `-> Location<0, glam::Vec4>`.
- **Имя entry = имя Rust-функции** (`fn vs_main` → `fn vs_main`);
  `entry = "…"` остался опциональным оверрайдом, пользователей — ноль.
  Неймспейс замкнут: `{vs_main, fs_main}` на 11 entry.
- **Контракты:** bundle-структуры + `#[derive(ShaderContext)]`
  (`GLOBALS`); тесты `stage_globals_declared` (30 имён против сборок),
  `interface_field_order` (порядок полей литералов vs зеркал),
  `entry_points_match_pass_abi` (ABI попасно, не множеством).
  Renderer и `composite.rs` просят entry через `entry_point()`-аксессоры —
  литералов ноль.
- **Сборки** — обычные функции (`wgsl_source()`): типы — naga IR через
  derive (`naga_add_type`), ресурсы — таблицы `Resource` (WGSL-decl +
  `wgpu::BGL` из одного места), константы — const-expression композиты
  (`const quad`/`const uvs`, lowercase чтобы поле === глобалу).
  Известный workaround: writer naga 30 печатает load-only storage как
  голый `var<storage>` (баг `address_space_str`, в IR не решается) —
  постфикс с тестом-пином.
- **Честные границы:** proc-макрос не видит чужих item'ов — соответствие
  «поле → глобал» enforced тестами, не макросом; DSL — Rust-authored WGSL,
  не transpiler (функции не исполняются, семантика на naga/тестах);
  тела entry — DSL-only (шаг «валидный Rust» ниже).

## 2. Принятые решения (журнал)

- **Компромисс по naga (2026-09-08):** `Rust declarations → naga IR`,
  `Rust expressions/functions → собственный Shader IR → WGSL`,
  `naga → финальная валидация`. Не переводить тела на ручной naga IR
  насильно — источник всё равно Rust AST; функции — позже, если появится
  выгода. Отдельный writer и семантический слой (`wgsl.rs → Shader IR`,
  `wgsl_ir.rs`, `wgsl_writer.rs`) — следующим большим рефакторингом,
  когда DSL упрётся, а не наоборот.
- **Типизированный контекст (2026-09-09, бандлы 2026-09-10):** bundle-форма вместо
  per-param `#[wgsl(global)]` и свободных идентификаторов; вложенные
  бандлы — вторыми `Context<T>`-параметрами (`consts: QuadConsts` →
  `consts.quad[idx]`, `maps: LightingMaps` → `maps.albedo_tex`), детект
  wrapper'а generic'ом — ноль изменений макроса. Принцип: бандл, когда
  группа оправдывает свой сегмент (семплируемые карты с общим сэмплером,
  всегда-вместе консты); ≤6 полей — плоско. Поле === глобал, без
  маппинга; трёхуровневые `ctx.camera.view_proj` — поля глобалов, не
  бандлы (стриппер снимает один уровень под известным `ctx`). Типы полей — настоящие (`CameraUniform`,
  `Vec<PerObjectGpu>`) или номинальные DSL-маркеры (`Texture2d`,
  `Sampler`), никогда не инстанцируются.
- **Single-source entry (2026-09-09):** имя → Rust-идентификатор;
  renderer — через аксессуары; ABI попасно в тестах.
- **Порядок миграции (инверсия приоритетов):** сначала дешёвые шаги с
  compile-time эффектом (контекст → типы → резолвинг), собственный
  IR-писатель — последним. Диагностика указывает на Rust-выражение;
  round-trip тесты сохраняются на каждом шаге.

Целевое (без изменений):

```text
Rust declarations ───────┐
                          ├─> Shader module ─> WGSL writer ─> naga
Rust functions ─> AST ───┘       (IR)
```

Требования к движению: Rust — главный источник истины (layout'ы,
интерфейсы, ресурсы, функции, entry); `format!` уходит из семантического
слоя; постобработка WGSL — только задокументированные workaround'ы;
типы/builtins — через symbols, не таблицы строк; до печати — место под
passes оптимизации/валидации.

## 3. Что дальше (по приоритету)

1. **«Валидный Rust» в телах:** выполнен первым срезом —
   `stage_field_uses_resolve` сверяет все не-свизловые `root.field` в
   entry против настоящих определений (`FIELD_NAMES` layout'ов,
   `WGSL_FIELDS` зеркал, `OPENPBR_SLOTS` для `mat`; 151 использование,
   неразрешённый корень — ошибка). Без моков и второго lowering'а:
   оракулы — реальные определения, текст — реальный выхлоп.
   Полная компиляция тел отклонена: orphan-правило запрещает
   `Index<VertexIndex>` для массивов/Vec, DSL-конструктор
   `Vec2::new(x)`-splat расходится с glam, а ~25 моков с угаданными
   сигнатурами дадут ложную уверенность вместо проверки.
   2026-09-10: пункт закрыт как SUPERSEDED — замер показал ~36
   цветных свизлов (`.rg`, `.a`, …) в телах, несовместимых с реальным
   glam (там только `.xyzw`), т.е. честная проверка требует либо
   фейковую числовую башню (та самая ложная уверенность), либо
   переписывание тел под Rust-спеллинги с churn'ом WGSL-текста.
   Матрица покрытия показывает, что rustc ничего не добавит — каждый
   класс ошибок уже ловится: синтаксис — парсингом `syn` (spanned),
   арность — препроходом `check_builtin_arity` (spanned), опечатки в
   вызовах — `stage_calls_resolve` (85) + naga (`no definition`),
   опечатки в ресурсах — `stage_globals_declared` (30) +
   `stage_resources_visible_at_stage` (28) + naga, типы (`vec3` vs
   `vec2`) — naga (WGSL типизирован), порядок полей — тест
   `interface_field_order`, номера биндингов — конструкцией (BGL и
   `bind_group_entries` из таблиц, не проверкой), поведение — 5/5
   пиксельных проб. Вне всех гейтов только same-type перестановки
   аргументов (`mix(a,b,t)` vs `mix(b,a,t)`) — их rustc тоже не ловит
   (шим примет оба). naga — тайпчекер DSL, и он уже в цикле.
2. **`ShaderType`/`TypeId` + enum builtin'ов** — выполнено:
   `shader_lang.rs` (`ShaderType`: скаляры/векторы/матрицы + `Quat`/
   `Vec2A`-алиасы; `ShaderBuiltin`: 36 вариантов с арностью,
   `lerp→mix` в одном месте вместо двух таблиц). Шесть разрозненных
   match-таблиц схлопнуты, `bool` исключён из примитивов (выхлоп тот же
   через старые фолбэки), неверная арность (`dot(x)`, пустой
   `length_sq`) — spanned-ошибка препрохода вместо наги/паники.
   Кернелы/нативные WGSL-имена идут мимо реестра verbatim, как раньше.
3. **Типизированный резолвинг:** выполнен тест-временным срезом —
   `stage_calls_resolve` (85 вызовов: builtins через общий реестр
   `ornis-shader-lang`, нативы, конструкторы, `fn`/`struct` из той же
   сборки; общий крейт-реестр понадобился, т.к. proc-macro крейты не
   экспортируют items) и `stage_resources_visible_at_stage` (28
   table-backed чтений против `visibility`; consts скипаются).
   Вложенные контексты разблокированы следующим шагом.
4. **Декларативный pass-объект** (бывший §3): один объект вместо
   пяти рассинхронизированных мест (таблица, header, BGL, decls,
   runtime binding). Выполнено полностью: `ShaderModule`-билдер
   (секции types → resources → consts → helpers → entries, порядок
   зашит в `emit`, call sites объявляют ЧТО); ручные `format!`-скелеты
   удалены из всех 9 сборок, 7 orphan-обёрток (`vertex_bindings`,
   `fragment_bindings` ×2, `bloom_header_head`, `composite_header_rest`,
   `fragment_head`, `vertex_quad_uv`) инлайнены; `bind_group_entries`
   строит runtime-биндинги из тех же таблиц (номера — из таблицы,
   call site маппит только имя → живой ресурс, 8 сайтов, дрейф доказан
   отсутствием пикселями). Полный `#[shader_pass]` — по необходимости,
   не ради синтаксиса.
5. **Разделить lowering и печать** — выполнено: `syn` строит IR, не
   `format!`. `ornis-shader-lang/src/{ir,writer}.rs` (`IrExpr` 17
   вариантов, `IrStmt` 5, `IrBinOp` 26, `IrCallee`
   Constructor/Builtin/Verbatim/Expr; writer владеет всеми WGSL-спеллингами
   включая квирки `/* names */`, `; `, `else {  }`), lowering в
   `macros/src/wgsl_lower.rs` (чистая функция `syn` → IR: calls
   классифицируются: конструкторы/`ShaderBuiltin`/вербатим; `powi`
   раскрывается в `Binary`-цепочку, свизлы — в `Field`, касты прозрачны),
   `wgsl.rs` ужался до фасада (~150 строк против ~1000: `WgslGen::expr`,
   типы, фрейминг `fn`/compute, те же публичные сигнатуры).
   Доказательства: все существующие exact-string тесты прошли БЕЗ правок
   (байт-идентичность), плюс структурные тесты lowering
   (`lerp` → `Builtin(Mix)`-узел, `powi(2)` → `Mul`-цепочка,
   `let = if` → 2 стейтмента) и writer-тесты в `shader-lang` (13/13) —
   трансляция впервые тестируема без строк. В траверсе ноль `format!`
   (остались только лексика литералов и фрейминг сигнатур).
6. **Расширять подмножество Rust** — закрыт как on-demand: все 11 entry
   транслируются, ни одно тело не требует недостающих конструкций
   (`match`/циклы-шаги/итераторы отсутствуют в шейдерах по факту, а не
   по запрету). Новые конструкции — когда появится тело, которому они
   нужны; IR-граница делает расширение аддитивным (узел + lowering +
   writer), а не правкой траверса.
7. **Compute-DSL для solver-grade кернелов (закрыто 2026-09-15):** `ShaderType::Mat3` (`mat3x3<f32>`; конструктор
   `Mat3::from_cols` — порядок колонок совпадает с WGSL,
   у `from_rows` прямого спеллинга нет и он громко отвергается;
   `Mat3::IDENTITY`/`ZERO`); локальные фикс-массивы
   (`let mut d: [f32; 6] = [0.0; 6];` → `var d: array<f32, 6>`, вложенные
   для гессиана; repeat — только литералы/константы/вложенные формы с
   капом 1024, эффекты молча не переупорядочиваются);
   `helpers(a, b)` в `#[gpu_pipeline]` — стыковка `wgsl_source()`
   хелперов (`#[wgsl_fn]`/`#[kernel]`) впереди entry: proc-макрос не
   видит чужих item'ов, поэтому это конкатенация в runtime, а не инлайн;
   без хелперов `wgsl_source()` остаётся `&'static str`, с ними —
   `String`). Пины: `macros/tests/compute_dsl.rs` (включая naga-валидацию
   LDL-формы 3x3), юниты парсинга `helpers`, physics-тест
   `helpers_stitch_ahead_of_main_and_validate` (gpu-фича).
   Декларации модуля — тоже IR (`IrItem`: storage/uniform/texture/sampler
   как `IrGlobal`, квад-константы, `VertexOutput`; закрытый `IrTexture`,
   типы entry-параметров по семантике из таблицы writer'а): парсинг
   `#[gpu_pipeline]` больше не склеивает WGSL-текст, сырой строкой
   остался только фрейминг сигнатур entry (как в `wgsl.rs`). По дороге
   пойман латентный баг старого шаблона: `const`-массивы нельзя
   индексировать динамически — QUAD/UVS теперь `var<private>`; дефолтный
   vs-параметр — скалярный `u32`, а не `vec3`.

## 3.1 Следующий этап: staged-метапрограммирование (решение 2026-10-17)

> **Статус:** направление выбрано, подтверждается спайком (см. ниже);
> спайк не начат, код не менялся. Обсуждение и разбор альтернатив —
> §4 («wasm», «rust-gpu») и §3.2 (идеи Slang).

**Диагноз.** AO/GTAO остались сырым WGSL (`ao_generated.rs`: «indexed
loops and `continue`, which the DSL does not cover»). Это закрывается
аддитивно (узел IR + lowering + writer). Корневая причина глубже:
proc-macro не видит типов и чужих item'ов. Следы в коде: `helpers(a, b)`
склеивает хелперы конкатенацией строк в runtime, хелперы
lighting/pbr/AO — рукописные строки, полная компиляция тел отклонена
(п.1: orphan rule, свизлы, моки с угаданными сигнатурами). Каждая
следующая возможность (модули, дженерики, трейты, общие хелперы) — это
Rust-фронтенд, дописываемый руками.

**Решение.** Макрос не парсит подмножество Rust и не печатает текст, а
разворачивает тело в обычный Rust-код, который **строит IR** (ваш
`IrExpr`/`IrStmt` или `naga::Module`, как уже делает `naga_ir.rs`) при
вызове. Прецедент — CubeCL (tracel-ai): `#[cube]`, стабильный Rust,
wgpu/WGSL на выходе. Следствия:

- вызов хелпера из другого модуля — обычный вызов функции, резолвит
  rustc; дженерики, трейты, `const` и модули работают без своего
  резолвера;
- роль макроса сводится к единообразному синтаксическому десугарингу,
  которому типы не нужны: `a < b` → `.lt()`, `if` → `select`/`branch`,
  `for` → `loop_range` (для фиксированных границ — разворот на
  трассировке: GTAO 2 слайса × 4 шага); типизирует rustc;
- нативный `if` на трассируемом значении не компилируется (у `Expr` нет
  `PartialOrd`/`bool`) — ошибка на сборке, а не молча зафиксированная
  ветка;
- spanned-ошибки на исходнике и stable-тулчейн сохраняются.

**Один источник, а не два.** Тело пишется один раз, обобщённо по
`S: Scalar`; инстансы: `f32` (CPU, мономорфизация без накладных
расходов), `Expr` (трассировка → IR → naga), опционально `wide::f32x4`
(SIMD-wide CPU; не проверено). Трейт — единственное «зеркало», его
сигнатуры проверяет компилятор, в отличие от отклонённых моков. Семантику,
где CPU и GPU расходятся (FMA-контракция, NaN в `min`/`max`, переполнение
целых, деление на ноль, `as`), трейт фиксирует в одном месте; реализация
для `f32` воспроизводит GPU-семантику там, где это важно. Паритет-тесты в
стиле `gpu_contact_row` остаются обязательными.

Сегодня у GTAO два источника: WGSL-строка `gtao_arc` и CPU-функция
`ao::gtao_sample`, связанные комментарием «the same closed form» и
тестом. Staged-подход убирает дубль.

**Граница «переносимого ядра».** Единый источник возможен только там, где
есть CPU-аналог: чистая математика (`contact_math`, `gtao_arc`, хэши,
falloff), циклы с фиксированными границами, `Mat3`/фиксированные
массивы. Ресурсы, текстуры, производные, барьеры, atomics и
workgroup-память — «GPU-оболочка»: у неё нет CPU-двойника, и моки
текстур не пишутся; проверяется она на lavapipe, как сейчас.

**Цены.**

- обобщённый код нужен над своими `Vec3<S>` либо над локальным трейтом
  векторных операций (`glam::Vec3` реализует его как CPU-инстанс — orphan
  rule не мешает, трейт свой); эргономика хуже (трейтовые границы вместо
  операторов), её надо мерить;
- переписывается lowering (`wgsl_lower.rs`); `ir.rs`/`writer.rs` и
  `naga_ir.rs` переиспользуются;
- паритет CPU/GPU остаётся предметом тестов, а не гарантией типов.

### 3.1.1 Способы подачи: явный `S`, скрытые generics (выбрано), подмена имён

Подмена смысла (типы, литералы, сравнения, `if`/циклы) есть в любом
staged-подходе; вопрос в том, где она живёт (решение 2026-10-17):

1. **Явный `S: Scalar` в сигнатуре.** Прозрачен, проверяется rustc;
   минимальный вариант для спайка.
2. **Скрытые generics — предпочтительный вариант.** Автор пишет
   `fn gtao_arc(h: f32, n: f32) -> f32`; макрос синтаксически заменяет
   `f32` на `S` и `Vec3` на `Vec3<S>`, оборачивает литералы (`lit(0.5)`)
   и сравнения, а `if`/`for`/`match` превращает в вызовы builder'а. Код
   выглядит как обычный CPU-код. Вызов другого ядра `helper(x)`
   резолвится сам: rustc выводит `S` по аргументам, макросу не нужно знать,
   ядро это или обычная функция. Именно generics решают резолвинг
   вызовов, поэтому убирать их «совсем» нельзя, а прятать от автора можно.
   Не проверено: вывод `S` для голых литералов (`gtao_arc(1.0, 2.0)`).
3. **Подмена имён (prelude swap).** Одно тело раскрывается дважды: нативно
   и в модуле, где `f32`/`Vec3` переопределены на GPU-типы. Generics нет, но
   вызов `helper(x)` на GPU-раскрытии должен указывать на GPU-версию
   хелпера, а макрос не видит чужих item'ов (та же стена, что у
   `helpers(a, b)`); обходы (парные модули, реэкспорты) хрупкие. Не берём.

Что спрятать нельзя (текст одинаковый, семантика нет): `&&`/`||` на GPU
вычисляют обе стороны; `as` и переполнение целых ведут себя иначе; циклы
с границами, известными на этапе компиляции, разворачиваются (раздутие
кода), для динамических нужен свой конструктор цикла; присваивание
внутри ветки не ложится на замыкания (две ветки захватывают `&mut`) —
нужна SSA-подобная перестройка в макросе; нужно отличать значения времени
компиляции от значений времени выполнения (в CubeCL для этого `comptime`).
Чем естественнее код, тем больше работы у макроса и тем хуже диагностика
(«expected `S`, found `f32`» там, где автор `S` не писал).

### 3.1.2 Долгосрочный вариант: «rust-gpu без nightly» через LLVM IR

Идеал — тот же исходник, собранный двумя компиляторами, без переписывания
тела. rust-gpu делает это через кодогенератор на nightly. Без nightly
доступны четыре стабильных уровня съёма: AST (proc-macro, до типизации),
MIR (`--emit=mir`: до мономорфизации, трейтовые вызовы не разрешены,
формат нестабилен), **LLVM IR** (`--emit=llvm-ir`: после мономорфизации и
оптимизаций, вызовы разрешены) и wasm (типы теряются, §4). Оптимальный —
LLVM IR.

Проба 2026-10-17 (стабильный `rustc 1.97.1`, `wasm32-unknown-unknown`,
`no_std`, `-C opt-level=3 -C panic=abort -C target-cpu=mvp --emit=llvm-ir`,
nightly не понадобился): GTAO-подобная функция (цикл по `&[V3]`,
`continue`, `sqrt`, `sin`, сравнение) дала ~15 видов инструкций (`load`,
`getelementptr`, `fmul`/`fadd`/`fsub`/`fdiv`, `fcmp`, `icmp`, `select`,
`phi`, `br`, `or`, `ret`); структура разобрана SROA в скаляры, `sqrtf`
пришёл как `llvm.sqrt.f32`, `sinf` остался вызовом (подменяется по имени),
`continue` стал обычными переходами. Язык трансляции конечен и мал — в
отличие от открытого «подмножества Rust» в макросе. Это игрушечное ядро,
не весь GTAO: текстуры и ресурсы в пробе не участвовали.

Что остаётся сложным:

- **итераторы как указатели:** цикл по срезу превратился в `phi ptr` с
  шагом 12 байт и `icmp eq ptr`; нужно восстановить «ресурс + индекс»
  (provenance через `phi`/`select`/`getelementptr`) — главная
  нетривиальная часть;
- структуризация control flow (naga требует структурного CFG);
- ресурсы и входы: атрибутов на параметрах (как `#[spirv(binding)]`) на
  stable нет — метаданные выдаёт proc-macro на функции + обёртка entry;
- libm-вызовы (`sin`/`pow`/`exp`) подменяются по символам, паники —
  в `discard`/`unreachable`, bounds-check снимается;
- uniformity (LLVM может переставить вызовы, требующие равномерного
  control flow);
- дрейф текста LLVM IR между версиями Rust (смягчается закреплённым
  `channel = "1.97"`); парсер — свой для нужного подмножества либо LLVM
  через `llvm-sys`/`inkwell` (тяжёлая системная зависимость);
- по объёму это отдельный компилятор, сопоставимый с SPIR-V-фронтендом
  naga, а не доработка макроса.

Общее для обоих путей и не зависящее от выбора: `#[derive(BindGroup)]`,
раскладка из naga (§3.2), `naga_ir.rs`, паритет-тесты CPU/GPU и граница
«переносимое ядро / GPU-оболочка».

### 3.1.3 Порядок и критерии

Основной путь — скрытые generics; LLVM-IR-проба параллельна и ограничена
по объёму; rust-gpu (§4) — запасной вариант, если обе окажутся хуже.

**Спайк A (скрытые generics).** Одно ядро — `gtao_arc` + horizon march,
по ступеням; на каждой меряется сложность макроса и читаемость ошибок:

1. явный `S` без переписывания тела;
2. скрытые generics: макрос переписывает типы, литералы и сравнения;
3. инстанс `f32` сравнивается с `ao::gtao_sample` (при успехе
   `gtao_sample` удаляется как дубль);
4. инстанс `Expr` → naga → lavapipe, расхождение с CPU в пределах
   нескольких ulp;
5. оценка эргономики: читаемость тела, ошибки трейтовых границ,
   количество правил переписывания в макросе.

Если ступень 2 даёт неприемлемые ошибки или раздувает макрос — основным
становится rust-gpu или LLVM-IR-путь.

**Проба B (LLVM IR → naga).** Взять функцию из пробы выше и перевести её
LLVM IR в `naga::Module` на нескольких десятках инструкций, с
восстановлением «ресурс + индекс» для цикла по срезу. Критерий: если
анализ указателей укладывается в небольшой крейт — LLVM-путь реальный
кандидат; если разрастается — остаются скрытые generics.

Тот же механизм «одно тело — `f32` / `f32x4` / `Expr`» снимает вопрос о
SIMD-кодогенерации ([#113](https://github.com/kemperrrrr/ornis/issues/113),
IDEAS §31): это ещё один инстанс трейта, а не отдельный преобразователь
AST.

## 3.2 Что взять у Slang (идеи, не зависимость)

Slang как зависимость не берём: это C++-библиотека и другой язык, а мы
теряем «один Rust-источник для CPU и GPU». Переносятся идеи:

1. **Группа ресурсов как структура (`ParameterBlock`).**
   `#[derive(BindGroup)]` над структурой с полями вроде `Uniform<Camera>`,
   `Storage<[Light]>`, `Texture2d<f32>`; индексы биндингов выводятся из
   порядка полей, группы выделяются по частоте обновления
   (frame / view / material / object). Это не отклонённые const-generic
   биндинги (§4): индекс не зашит в тип, а выводится. Заменяет ручные
   таблицы `Resource { group, binding, … }`.
2. **Раскладка считает один движок.** `naga::proc::Layouter` как
   источник; сверка с `offset_of!`/`size_of`, как в `WgslStruct`. `vec3`
   в storage — только через явный тип с паддингом, без автопаддинга.
3. **Модули и интерфейсы.** То, что в Slang решают `import` и
   `interface`, в staged-модели решают Rust-модули и трейты — своего
   резолвера не нужно.

Проблему «много биндингов» язык не снимает: она упирается в лимиты
WebGPU (по умолчанию 4 bind group, 8 storage-буферов и 16 sampled-текстур
на стадию; сверять со спецификацией). Рабочие приёмы — упаковка данных в
меньшее число буферов, texture arrays, атласы; группы по частоте
обновления помогают уложиться в 4 группы. Для браузерного редактора
(WebGPU/WASM) это важнее выбора языка шейдеров.

## 4. Отклонённые альтернативы (чтобы не возвращаться)

- **Rust → wasm → WGSL (2026-10-17).** Идея: stable-rustc даёт wasm, его
  переводят в WGSL. Отклонено: у naga нет wasm-фронтенда (входы SPIR-V,
  WGSL, GLSL), существующий `wasm2spirv` — экспериментальный. Wasm
  стирает информацию: структуры, `vec3`, `bool`, `u32` против `i32`;
  вся память — линейная и адресуется `i32`, а GPU нужны типизированные
  ресурсы и адресные пространства (shadow stack, alias-анализ, promotion
  стековых слотов — мини-оптимизатор); `sin`/`cos`/`pow`/`exp`/`fma` —
  вызовы libm, а не инструкции (в шейдер попал бы программный `sinf`);
  паники и bounds-check тянут `core::panicking`; LLVM не знает про
  uniformity WGSL (`textureSample`, барьеры); ошибки теряют spans.
  Информации строго меньше, чем у rust-gpu (MIR/типы) и у макроса
  (исходник). Если идти по пути «компилятор без nightly», вход лучше
  брать на уровне LLVM IR, а не wasm (§3.1.2).
- **rust-gpu как основной путь (2026-10-17) — запасной вариант.**
  Nightly изолируется (шейдерный крейт со своим `rust-toolchain.toml`,
  сборка через `spirv-builder` в xtask/CI, прецедент `exclude` для
  `third_party/rustqual`), поэтому не он главный довод против. Цены:
  `cargo outdated --exit-code 1` (шейдерный крейт тянет свои версии glam
  и др. — исключать из гейта); общий крейт CPU/GPU обязан собираться и на
  1.97, и на закреплённом nightly (`no_std`, ограниченные фичи); путь
  SPIR-V → naga `spv-in` → WGSL на WebGPU/WASM (основная платформа
  редактора) — главный технический риск, нужно проверять прототипом
  (валидация Tint в браузере); читаемость выходного WGSL и отладка через
  SPIR-V. Триггер пересмотра: провал спайка A (§3.1.3) по эргономике
  или потребность в коде с указателями/сложным control flow.
- **Бесконечное расширение macro-DSL как есть (2026-10-17).** Сегодня не
  потолок (`#[stage]` покрывает все entry, нехватка — отдельные
  конструкции), но не масштабируется на модули, дженерики и трейты: без
  типов и видимости чужих item'ов каждая такая возможность — отдельный
  самописный резолвер.

- **Build-time compiler (build.rs с парсингом исходников)** — дублирует
  proc-макросы без инкрементальности cargo, хрупок (cfg/алиасы/
  re-export/expansion). Всё нужное достижимо иначе (п.1–3 выше). Цена —
  аддитивное время сборки + проект кэширования ради паритета с
  бесплатным. Разбор от 2026-09-09.
- **Const-generic биндинги (`Uniform<0, 0, T>`)** — group/binding живут
  в одном массиве на пасс; зашивка в тип превращает правку layout'а в
  правку сигнатур. Имена возвращаются строками в билдере.
- **`shader_module!` (module-level DSL)** — мощный cross-item анализ,
  но нестандартный синтаксис ради задач, решаемых функциями-сборками.
- **«Избавиться от макросов» как цель** — закон сохранения метаданных:
  она переезжает, а не исчезает. Цель — убрать их из семантического
  кода (выполнено).
- **Налог `.0`** — newtypes живут только в сигнатурной позиции, тела
  используют голый идентификатор; отдельное правило lowering'а не нужно.
- **Маркер-типы entry (`EntryPoint`-трейты)** — макросу нужна строка в
  момент экспансии, чужой `impl` он прочитать не может: строка осталась
  бы в `entry` anyway, тип — второе написание того же. Выбран один
  источник (имя функции → WGSL → аксессуар → пайплайн).
- **Суперседы (было → стало, 2026-09-09):** per-param `#[wgsl(global)]`
  → `Context<T>`; `entry = "…"` → имя функции; `QUAD`/`UVS` → lowercase;
  legacy `vs`/`fs` → `vs_main`/`fs_main`; мёртвый `hdr_fragment_vs_entry`
  удалён; `#[wgsl(builtin/location)]` в entry — ноль (newtypes +
  struct-inputs).
