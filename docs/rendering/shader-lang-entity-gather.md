# Entity и read-only gathers в `#[kernel]` (RAT-49, feature 1)

Задача: https://github.com/kemperrrrr/ornis/issues/110 (часть 1 из 3).

## Проблема

`#[kernel]` — attribute macro: на этапе раскрытия он видит только синтаксис
функции и не видит определения структур компонентов. Поле чужой сущности
(`t.position` у `t: Entity`) имеет тип из определения `Position` — а макрос
этого определения не получает. Следовательно:

1. тип такого поля невозможно вывести внутри макроса;
2. у поля нет «родного» Rust-представления в kernel-модуле — только
   storage-lane на GPU.

Решение — контракт типа **на месте использования**: тип чужого поля задаётся
аннотацией читающего кода, и эта же аннотация является контрактом для
генерируемого WGSL и для CPU-зеркала `eval`.

## Модель

`Entity` — ручка (handle), а не ссылка на компонент:

```rust,ignore
pub struct Entity { pub index: u32, pub generation: u32 }
```

- `index` — слот в SoA-lane'ах вызывающего;
- `generation` — штамп поколения для CPU-проверок устаревания; **GPU
  индексирует lane'ы только по `index`** — проверка generation на стороне
  шейдера не выполняется (параллельность CPU/GPU; генерация — данные
  идентичности CPU).

`index` / `generation` — настоящие поля структуры с обеих сторон (WGSL
`struct Entity` и эмитируемый CPU-mirror), читаются напрямую (`t.index`),
аннотация не нужна.

Всё остальное поле на entity-биндинге — **gather**: чужое поле читается из
отдельного SoA storage-массива, по одному на пару `(биндинг, поле)`:

```wgsl,ignore
@group(0) @binding(0) var<storage, read> _ornis_lane_t__position: array<vec3<f32>>;
fn _ornis_gather_t__position(e: Entity) -> vec3<f32> {
    if (e.index >= arrayLength(&_ornis_lane_t__position)) {
        return vec3<f32>(0.0, 0.0, 0.0);
    }
    return _ornis_lane_t__position[e.index];
}
```

Проверка границ — **ранний return**, не `select` (обе ветви `select`
вычисляются — выход за границы массива дал бы OOB). Выход за границы даёт
элемент-ноль лейна — зеркально CPU.

## Контракт типа: аннотация на месте чтения

Допустимые позиции чтения чужого поля — ровно две:

1. **annotated let**: `let p: Vec3 = t.position;` — тип аннотации и есть
   тип лейна;
2. **хвост/`return` функции**: `fn f(t: Entity) -> Vec3 { t.position }` —
   тип берётся из типа возврата.

Всё остальное — spanned compile error в макросе, никогда не молчаливый
перевод:

| Отклоняется | Причина |
| --- | --- |
| `let p = t.position;` без аннотации | макрос не видит определение `Position` |
| `t.position.x` (вложенные чтения) | одна аннотация не может покрыть две проекции — сначала `let p: Vec3 = t.position;`, потом `p.x` |
| `t.position = …`, `t.position += …` | у чужого поля нет WGSL-записи; мутации — CPU-системой |
| методы на entity (`t.foo()`) | нет WGSL-произношения |
| ссылки (`&t`) | `Entity` — копируемое значение |
| `t == other` целиком | у WGSL нет равенства структур; сравнивайте `.index`/`.generation` |
| конфликтующие аннотации одного `(биндинг, поле)` | один лейн — один тип |
| `bool`/`BVecN` как элемент лейна | у storage-массива нет bool-представления; для флагов — `u32` |

Квалифицированные `foo::Entity` / `crate::Entity` в сигнатуре отклоняются
(`kernel_types`): `Entity`, как и `Option`, пишется bare. `Option<Entity>`
поддержан: лейн-элементом v1 не является, но `Some(e)` / `if let Some(e)`
биндинги порождают entity-биндинги, доступные для gathers.

Аннотация — это Rust-типы, и они должны резолвиться в порождённом модуле
`#fn_name` (как и типы сигнатур `#[kernel]` сегодня): для glam-типов
пишите полный путь `glam::Vec3`; примитивы (`f32`, `u32`) и сам `Entity`
резолвятся всегда.

## CPU-зеркало `eval`

`eval` зеркалит WGSL один-в-один: на каждый записанный лейн в конец
сигнатуры добавляется срез `&[T]`, а тело читает поля через ровно тот же
bounds-check:

```rust,ignore
fn _ornis_gather<T: Copy + Default>(lane: &[T], e: Entity) -> T {
    let i = e.index as usize;
    if i >= lane.len() { T::default() } else { lane[i] }
}
```

`T::default()` — элемент-ноль, тот же, что возвращает WGSL-хелпер.
Совпадение условий границ — инвариант: одна и та же строка `t.position`
читает один и тот же слот с обеих сторон при одинаковом `index`.

`Entity`-структура и `_ornis_gather` эмитятся в модуль `#fn_name` только
при наличии entity/gathers — ядра без `Entity` не несут накладных расходов.

## WGSL: имена, порядок, биндинги

- Все сгенерированные имена начинаются с **одного** подчёркивания: WGSL
  зарезервирует идентификаторы с двойным подчёркиванием (`__`).
- Лейны — **module-scope** `var<storage, read>`: naga отвергает
  `ptr<storage, …>`-параметры функций (`InvalidArgumentPointerSpace`).
- Порядок деклараций: `struct Entity` (если упомянута) → `struct
  Option_…` → lane-массивы → gather-хелперы → `fn`.
- Номера биндингов `0..n` назначаются в отсортированном порядке ключей
  `(биндинг, поле)` — детерминированно. Ренумерация при композиции
  нескольких kernel-модулей в один шейдер — отложенный пункт (см. ниже).
- Форма `wgsl_source` (standalone): Entity + Option + лейны + хелперы.
  Форма `wgsl_compute_source` (legacy compute): без лейнов и хелперов —
  gather в ней не поддержан и падает громко на naga-стадии; см.
  «Отложено».

## Проверка

Интеграционные тесты `crates/macros/tests/kernel_entity_gather.rs`
проверяют каждое ядро **дважды**: CPU `eval` исполняет настоящий Rust-тело
против `&[T]`-лейнов, а сгенерированный WGSL парсится и валидируется naga.
Перевод, который «выглядит правильно», не пройдёт — одна и та же строка
исполняема с обеих сторон. Отклонения закреплены trybuild-тестами
(`kernel_rejects_unannotated_gather`, `…_gather_write`, `…_bool_lane`,
`…_entity_eq`, `…_nested_gather`).

## Отложено (вне RAT-49 feature 1)

- **Lane-биндинги в compute-форме** — требуют протокола привязки
  storage-массивов к legacy-пути.
- **`derive(Pack)`-интеграция** — закрыто feature 2 (RAT-50): колонки
  `#[pack(gpu)]`-бандлов автоматически становятся storage-лейнами
  `#[gpu_pipeline(pack(T))]`; контракт —
  `docs/rendering/shader-lang-pack-lanes.md`. Учтите: индекс-пространства
  **не связаны** — gather-лейны (`_ornis_lane_…`, индекс =
  `Entity.index`, слот в вызывающих lane'ах, см. «Модель») и pack-лейны
  (индекс = позиция в возрастающем порядке id, см. pack-lanes.md) в v1
  независимы; совпадают только при плотных id `0..n` без удалений.
- **Ренумерация биндингов при композиции** — когда несколько
  kernel-модулей склеиваются в один shader string, номера биндингов
  должны переиндексироваться по единому протоколу.
- **Разделяемый `Entity` между kernel-модулями** — сейчас каждый
  `#[kernel]` эмитит собственный CPU-`Entity`; на GPU структура
  идентична, но типы Rust между модулями не совместимы.
- **`Option<Entity>` как элемент лейна** — в v1 не поддержан.
