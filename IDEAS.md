# Ключевые идеи игрового движка на Rust

> Извлечено из концептуального диалога о проектировании движка.  
> Дата: 24–25 июня 2026 г.

> ⚠️ **Обновление (июль 2026):** Нативный UI-крейт заморожен. Ключевая идея №5 (Headless DOM) сохранена ниже в историческом контексте, но текущая реализация — браузерный редактор + WebGPU/WASM.

## 1. «Невидимый ECS» (Transparent ECS) — скрытая SOA-трансформация

- **Проблема**: классические ECS (Bevy, Unity DOTS) требуют от программиста думать категориями «систем», «компонентов» и «запросов», что создаёт высокий порог входа и много бойлерплейта.
- **Решение**: процедурные макросы Rust автоматически преобразуют обычный объектно-ориентированный код (Array of Structures, AoS) в Struct of Arrays (SOA) на этапе компиляции.
- **Для пользователя**: он пишет привычный `for entity in entities { entity.position += entity.velocity; }`, а под капотом данные уже хранятся в раздельных плотных массивах (архетипы/лены), обрабатываемых оптимально для CPU-кэша.

---

## 2. Sparse Sets вместо Архетипов

- **Проблема архетипов (Bevy/Unity)**: при изменении состава компонентов сущности (добавление/удаление баффа, дебаффа) движок вынужден физически копировать данные между блоками памяти, что вызывает аллокации и просадки производительности.
- **Решение**: отказ от архетипов в пользу **Sparse Sets** (разреженных массивов).
  - Каждое поле структуры — независимая «конвейерная лента» (плотный массив `data` + разреженный `sparse` индексатор).
  - Добавление нового поля сущности = мгновенная запись в конец массива + обновление таблицы перевода. Никакого копирования блоков памяти.
  - Процессор обрабатывает плотные массивы подряд, что идеально для кэш-локальности и GPU.

## 2.1 ZST-маркеры конвейеров (Zero-Cost Type-Safe Dispatch)

- **Проблема**: выбор CPU/GPU для ленты — это рантайм-решение (`match` / `if`), который тратит циклы и мешает инлайнингу.
- **Решение**: Zero-Sized Types (`GpuLane`, `CpuLane`, `HybridLane`) как маркеры, связанные с типом компонента через трейт `LaneTarget`.
  - `impl LaneTarget for Position { type Target = GpuLane; }`
  - `GpuLane` — ZST, не занимает память в структурах, но компилятор использует его для статической диспетчеризации.
  - Выбор конвейера происходит **на этапе компиляции**, без `if` в рантайме. Компилятор вставляет нужный код (Rayon или WGPU) прямо в точку вызова.
- **Философия**: Borrow Checker + ZST = типобезопасная архитектура без оверхеда. Это соответствует духу Rust лучше, чем runtime-флаги или unsafe-указатели.

## 2.2 Гибридная структура данных: Sparse Sets + Bitsets + Paginated Arrays

Sparse Sets — сильный фундамент, но у них есть два слепых пятна при масштабе: пересечение множеств и избыточная память sparse-индексатора. Решение — гибрид, который сохраняет сильные стороны Sparse Sets и устраняет слабые через два дополнительных механизма.

### Bitset Acceleration для intersection-запросов

- **Проблема**: `Query<(&Position, &Velocity, &Health, Without<Dead>)>` на Sparse Sets требует пересечения 4 плотных массивов — линейный обход с прыжками по памяти.
- **Решение**: каждая лента хранит `FixedBitSet` (битовая маска), где бит `i` = 1, если сущность `i` имеет этот компонент.
- **Пересечение**: перед итерированием dense-массивов делается SIMD-friendly bitwise AND битсетов. Результат — список "живых" индексов, по которым уже идёт плотный обход.
- **Преимущество**: пересечение 4 массивов из 100k элементов превращается из `O(n)` с кэш-промахами в `O(n/64)` — векторизованная операция на 64 сущности за раз.

### Paginated Sparse Arrays для экономии памяти

- **Проблема**: 1M сущностей, компонент Poison есть только у 100 из них. Sparse Set тратит `1M * 8 байт = 8 МБ` на пустой индексатор.
- **Решение**: вместо одного гигантского `Vec<usize>` — страницы по 4K элементов (`Page<K>`). Страница выделяется лениво, только при первом обращении к любому индексу внутри неё.
- **Преимущество**: 99.9% страниц вообще не выделены. Память для разреженных компонентов падает с мегабайт до килобайт.
- **Трейдофф**: random access становится двухуровневым (`page_id → offset_in_page`), но всё ещё O(1) и кэш-эффективным, потому что hot pages остаются в L1.

### Итоговая структура

```rust
pub struct ComponentStore<T> {
    pub data: Vec<T>,           // Dense — итерация, GPU, prefetcher
    pub entities: Vec<Entity>,  // Обратная карта dense → entity
    sparse: PageTable<usize>,   // Paginated: страницы по 4K, ленивое выделение
    bitset: FixedBitSet,        // Битовая маска для SIMD intersection
}
```

**Почему это лучше чистых Sparse Sets:**
- Итерирование одной ленты — идентично (плотный `data`).
- Пересечение многих лент — в 10–50x быстрее (bitset AND).
- Разреженные данные — тратят память пропорционально occupancy, а не max_entity_id.
- GPU-маппинг — не затронут: `data` остаётся плотным `Vec<T>`.

**Почему это лучше Archetypes:**
- Мутация остаётся O(1) — нет Archetype Move.
- Каждая лента независима — нет фрагментации памяти на 100+ мелких блоках.
- GPU-конвейер не требует "сборки" данных из разных блоков.

**Референс:** EnTT (C++, используется в Minecraft Bedrock) использует именно этот гибрид: sparse arrays для storage, bitsets для queries.

## 3. Автоматическая многопоточность (CPU)

- **Идея**: макрос `#[smart_pipeline]` анализирует тело функции на этапе компиляции и, если итерации независимы, автоматически генерирует параллельный код через `rayon`.
- **Правила безопасности для макроса**:
  1. Независимость итераций (нет обращений к `entities[i+1]`).
  2. Отсутствие разделяемого изменяемого состояния (внешние переменные превращаются в атомики или `reduce`).
  3. Проверка трейтов `Send`/`Sync` для компонентов.
- **Параллелизм задач**: если две функции работают с разными полями, макрос может запускать их одновременно через `rayon::join`.

## 4. Унифицированные вычисления CPU ↔ GPU (Auto-Compute)

- **Идея**: один и тот же код на Rust компилируется либо в многопоточный CPU-конвейер (rayon/SIMD), либо в WGSL-шейдер для GPU, в зависимости от макроса или эвристик.
- **DSL-подмножество (Compute-Subset)**: вместо попытки транслировать весь Rust в WGSL (что привело к стагнации проекта Rust-GPU), создаётся строгое embedded DSL внутри макроса `#[kernel]`.
  - Разрешено: арифметика, векторная математика, условия без сложного control flow.
  - Запрещено: `Vec`, `String`, `Box`, рекурсия, динамическая аллокация. Макрос выдаёт понятную ошибку компиляции: *«операция `String::push` не поддерживается в контексте kernel»*.
  - DSL проверяется на этапе компиляции, и только валидный код транслируется в WGSL.
- **Механизм**:
  - `#[cpu_pipeline]` — генерация Rayon-кода.
  - `#[gpu_pipeline]` — трансляция AST функции в WGSL через `wgpu`.
  - `#[smart_pipeline]` — динамический или статический выбор исполнителя.
- **Data Residency (умные буферы)**: система отслеживает, где актуальные данные (CPU RAM или GPU VRAM), и копирует их только при необходимости, избегая «захлеба» по шине PCIe.
- **Порог переключения**: гибридный подход. Статический профайлер генерирует формулу `cost(n)`, а runtime подставляет `n` (количество элементов) и выбирает исполнителя. При первом запуске микро-бенчмарки калибруют константы под конкретное железо.

## 4.1 Статический профайлер (Compile-Time Analyzer)

- **Проблема**: runtime-эвристики (типа «много математики = GPU») ошибочны и тратят процессорное время на принятие решений каждый кадр.
- **Решение**: макрос `#[derive(PipelineConfig)]` или `#[analyze]` выполняет **анализ AST на этапе компиляции** и принимает статические решения.
- **Что анализируется**:
  1. **Размер типа**: `std::mem::size_of::<T>()` — через `const` контекст. Большие структуры (>256 байт) → CPU, мелкие примитивы → GPU.
  2. **Типы полей**: рекурсивный анализ AST (`syn::Type`). `Vec`, `String`, `Box` → CPU (WGSL не поддерживает), `f32`, `Vec3`, `i32` → GPU.
  3. **Control flow**: подсчёт `if`, `match`, `loop`, `while`. Высокое соотношение ветвлений → CPU (Branch Divergence).
  4. **Access pattern**: сколько лент читается/пишется. 1–2 ленты чистой математики → GPU, 5+ лент → CPU.
  5. **Трейты**: проверка `Send + Sync`. Нет `Sync` → только CPU.
  6. **Рекурсия**: проверка вызовов функций внутри себя. Рекурсия → CPU.
- **Результат**: сгенерированный `const fn threshold<T>() -> usize` и `const fn lane_target<T>() -> TargetDiscriminant`, которые рантайм использует для финального выбора. Но самое важное решение (куда отправить ленту) уже принято на этапе компиляции через ZST-маркеры.

---

## 4.2 Сортировщик конвейеров (Pipeline Router)

- **Идея**: после SOA-разложения (этап 1) добавляется **третий этап конвейера** — сортировка по исполнителям (CPU/GPU).
- **Как работает**:
  - `Position` (vec3, 12 байт, чистая математика) → GPU lane.
  - `Health` (f32, но используется в `if/else`) → CPU lane.
  - `Inventory` (72 байта, `Vec<Item>` внутри) → CPU lane.
  - `UIStyle` (редко меняется, не нужна GPU) → CPU lane.
- **Гибридный подход**: статический профайлер генерирует **формулу решения**, а runtime подставляет `n` (количество элементов). Для `Position`: `element_count > 10_000 → GPU, иначе CPU`. Для `Health`: всегда CPU, независимо от размера.
- **Дополнительный слой абстракции**: движок перестаёт быть просто «исполнителем» и становится **«оптимизирующим компилятором с рантаймом»**.

## 4.3 Инструкции вместо данных (Command-Based Sync)

- **Проблема**: даже с Data Residency постоянное копирование массивов float'ов по PCIe — это узкое горлышко.
- **Решение**: вместо гонки данных туда-обратно, отправлять **инструкции** (описания операций) туда, где данные уже лежат.
- **Механизм**:
  - CPU отправляет не `[1.2, 3.4, 5.6, ...]`, а команду: «для всех сущностей с Position примени `gravity(dt)`».
  - GPU исполняет Compute Shader над уже лежащими в VRAM данными.
  - `wgpu::CommandBuffer` и `ComputePass` — нативный механизм для этого. CPU записывает список команд, GPU исполняет асинхронно.
  - Синхронизация происходит только для тех сущностей, которые **реально нужны** другому процессору (например, коллизии для CPU-логики).
- **Преимущество**: данные живут там, где созданы. Если `Position` генерируется процедурно на GPU — оно там и остаётся. CPU только «шлёт указания».

## 4.4 Zero-Cost Dispatch через ZST (Runtime без if)

- **Проблема**: даже после всех оптимизаций, остаётся вопрос — как в рантайме выбрать конкретный исполнитель, не тратя циклы на `match`?
- **Решение**: ZST-диспетчеризация. Трейт `ExecuteLane` реализуется для `GpuExecutor` и `CpuExecutor` (оба — ZST). Макрос генерирует связь: `Position → GpuExecutor`, `Health → CpuExecutor`.
- **Пример**:
  ```rust
  trait ExecuteLane { fn execute(store: &SmartStore); }
  struct GpuExecutor; // ZST
  struct CpuExecutor; // ZST
  impl ExecuteLane for GpuExecutor { /* wgpu compute pass */ }
  impl ExecuteLane for CpuExecutor { /* rayon par_iter */ }
  
  // T::Executor — ZST, выбор произошёл на этапе компиляции
  fn run_system<T: LaneTarget>() { T::Executor::execute(store); }
  ```
- **Результат**: в рантайме **нет ни одного `if` или `match`** для выбора CPU/GPU. Компилятор знает заранее и вставляет нужный код. Это буквально zero-cost abstraction.

## 5. Headless DOM — UI на HTML/CSS/JS без тяжелого браузера

> **Статус (июль 2026):** Нативная реализация заморожена. Текущий путь — браузерный редактор + WebGPU/WASM.

- **Проблема**: Electron и встроенные браузеры (Chromium) тяжелые (150+ МБ), вызывают микрофризы и требуют сложной кроссбраузерной верстки.
- **Былое решение**: не писать браузер с нуля, а использовать **Servo** (браузерный движок Mozilla на Rust) или его компоненты как библиотеку.
  - HTML/CSS/JS парсится и исполняется полноценно (`html5ever`, `cssparser`, `SpiderMonkey` через Servo).
  - Результаты layout (координаты, стили) не рисуются через собственный рендерер Servo, а попадают в `ComponentStore<UIStyle>`/`ComponentStore<Rect>`, а оттуда — в `wgpu`-конвейер движка.
  - Вес вырастет до 50–80 МБ (вместо 10–15 МБ), но это всё равно в 2–3 раза легче Electron и полностью оправдано полной совместимостью с фронтендом.
- **Полная совместимость**: цель — не «ещё один проприетарный UI», а «фронтендеры пишут на привычном React/Vue». Игровые движки умирают из-за отсутствия талантов, готовых учить их UI-фреймворки. HTML/CSS знают все.
- **Интерпретатор JS**: `Boa` / `Rquickjs` / `QuickJS` выполняет React/Vue/чистый JS внутри Rust-процесса.
- **Глобальный «обман»** (`globalThis.document`, `window`) — шим, перехватывающий `createElement`, `appendChild` и т.д., и перенаправляющий их в Rust-ядро.
- **Rust-парсеры** (`html5ever`, `lightningcss`, `Taffy`) превращают HTML/CSS в геометрию, а `wgpu`/`Vello` рендерят UI напрямую в текстуру/экран через GPU.
- **Результат (исторический)**: идентичные пиксели на всех платформах, 144+ FPS, и главное — полная совместимость с существующей фронтенд-экосистемой.

### Почему заморожено

После реализации базовой инфраструктуры стало ясно, что доведение собственного UI-движка до production-уровня требует ресурсов, сопоставимых с командой браузерного движка. `boa_engine` ещё не проходит полный ECMAScript testsuite, `blitz` (Dioxus-рендерер) ещё не зрел. Вместо борьбы с багами нативного рендеринга принято решение:

1. **Редактор работает в браузере** — обычное веб-приложение на привычном стеке (React/Vue/Svelte).
2. **Сцена рендерится в браузерный `<canvas>`** через WASM + WebGPU.
3. **Исторический код `crates/ui` удалён из рабочего дерева** — при зрелости blitz/boa к нему можно вернуться через git-историю.

Это позволяет сосредоточиться на ядре движка (ECS, GPU-диспетчер, физика, аудио) — там, где реальное конкурентное преимущество.

## 6. Мультискриптинг — выбор языка для игровой логики

- **Ядро**: Rust (управление памятью, Sparse Sets, GPU-шейдеры).
- **Интерфейс**: HTML/CSS/JS (React/Vue/Svelte) в браузерном редакторе; нативный Dioxus/Blitz-путь заморожен вместе с прежним UI-стеком.
- **Скриптинг на выбор**:
  - **Python** — `PyO3` / `RustPython` (для геймдизайнеров).
  - **JavaScript** — `Boa` / `Rquickjs` (для UI-логики и веб-версий).
  - **Rust-подобные** — `Rune` (байт-код, полный синтаксис Rust) или `Rhai` (безопасный, лёгкий, многопоточный).
- **Принцип**: FFI-биндинги оборачивают переменные скриптов в прямые указатели на ячейки Sparse Set, исключая накладные расходы.

## 7. Автоматический конвейер ресурсов (Asset Pipeline)

- **Без атрибутов**: программист не размечает каждый файл макросами. Достаточно положить файлы в папку `/assets` (в ранних набросках использовалось имя `/ui`).
- **Build-Time** (`build.rs` или `#[compile_frontend_pipeline!]`):
  - Сканирует `/assets`, парсит CSS (`lightningcss`), SVG (`usvg`), HTML (`html5ever`), JS.
  - Генерирует Rust-структуры и бинарные слепки для Sparse Sets.
  - Вшивает JS-скрипты в бинарник через `include_bytes!`.
- **Runtime Hot Reload**: в режиме разработки `notify` отслеживает изменения файлов и мгновенно обновляет данные в лентах `ComponentStore<UIStyle>` без пересборки.

---

## 8. Адаптер для сторонних библиотек (Zero-Modification)

- **Проблема**: сторонние крейты (`rapier3d`, `noise`, `pathfinding`) не знают про Sparse Sets и используют обычные структуры AoS.
- **Решение**:
  - **Auto-Generated Proxy Views**: макрос `for_each_entity!` генерирует временные легковесные прокси-структуры прямо в L1/L2 кэше процессора, скармливает их чужой функции и возвращает результат в ленты.
  - **Inlining (растворение границ)**: компилятор Rust встраивает чужую функцию напрямую в `zip`-цикл по Sparse Sets, убирая накладные расходы на вызовы.
  - **Защита**: если чужой код неоптимален или содержит ветвления, он остаётся на CPU в изолированном Rayon-конвейере, не ломая GPU-поток.

---

## 9. Встроенный линтер (Compile-Time Static Analysis)

- **Проблема**: программист может не знать архитектуру движка и написать неэффективный поштучный доступ `store.get_mut(id)` в цикле.
- **Решение**: процедурный макрос `#[smart_pipeline]` анализирует AST функции через `syn` + `quote`. При обнаружении медленных паттернов выдаёт предупреждение через deprecated-note трюк, которое видно в IDE и терминале.
- **Цель**: обучать разработчика в процесс написания кода, не ломая сборку и не замедляя рантайм.

---

## 10. Полная универсальность платформ (Desktop + Web)

- **WGPU/WebGPU**: один код рендеринга работает на Windows (Vulkan/DX12), macOS (Metal), Linux (Vulkan), а в браузере — через WebGPU.
- **WASM**: компиляция движка в `wasm32-unknown-unknown` позволяет запускать игру и редактор в браузере без DOM-манипуляций — только `<canvas>` и WebGPU.
- **Единый пайплайн**: игровой мир и UI рисуются в одном `wgpu`-конвейере, что исключает микрофризы и позволяет накладывать игровые шейдеры на UI-элементы.

## 11. Метафора «Конвейерная сортировка»

- Вся архитектура строится на аналогии с сортировкой и конвейерами:
  - **Этап сортировки**: структура `Entity { position, velocity, health }` раскладывается на независимые «ленты» (массивы `position`, `velocity`, `health`).
  - **Этап конвейеров**: каждая функция получает только нужные ленты, не загружая в кэш лишние данные.
  - **Проекции (View-структуры)**: функция `apply_gravity` видит только ссылку на массив `position`, даже если исходная структура содержит 20 полей.

## 12. «Чёрный ящик» для стороннего кода

- Для макроса любая сторонняя функция — это «чёрный ящик» с входными и выходными данными.
- Макрос не пытается понять внутреннюю логику функции, а оптимизирует **подачу данных** в неё:
  - Красивая математика → GPU (Compute Shader).
  - Запутанная логика с `if/else` → CPU (Rayon-конвейер).
- Borrow Checker Rust гарантирует, что чужая функция не выйдет за пределы выделенных ей лент.

## 13. Entity Recycling + Generational Indices (память + безопасность)

- **Проблема**: монотонный `next_entity_id: u32` — после 4 млрд сущностей обернётся; удалённая сущность с `id=42` оставляет «дупло» в sparse-индексаторах всех лент.
- **Решение**: сущность хранит `(id: u32, gen: u32)`. При удалении `gen` инкрементируется, ID кладётся в `free_list`. При создании ID берётся из `free_list`. `get(entity)` проверяет совпадение поколений — use-after-free невозможен.
- **Экономия**: 1M созданий/удалений ≈ 1M активных ID, а не 2M; sparse-индексаторы не расширяются бесконтрольно.

## 14. Cache-Line Alignment (скорость)

- **Проблема**: `Vec<f32>` для `Position { x, y, z }` — 12 байт. Кэш-линия CPU = 64 байта. В одной линии помещается 5 сущностей, 6-я «вылезает» на следующую.
- **Решение**: `#[repr(align(64))]` и padding до 16/32/64 байт — ровно 4 сущности на кэш-линию.
- **Tradeoff**: +25% памяти на padding, но если `Position` читается в 80% систем — окупается.

## 15. Chunked Iteration (кэш-оптимальность)

- **Проблема**: `rayon::par_iter_mut()` делит массив на равные части. Но системы читают 3+ ленты одновременно — кэш «мечется» между массивами.
- **Решение**: обрабатывать чанки по 1–4 кэш-линии вместо поэлементного обхода. CPU prefetcher подхватывает следующий чанк, пока текущий обрабатывается.
- **Прирост**: 15–30% на CPU-bound операциях (EnTT-бенчмарки).

## 16. Lock-Free SmartStore (вместо RwLock)

- **Проблема**: `RwLock<ComponentStore<T>>` — блокировка даже при бесплатном чтении. При высоком contention (UI-поток + 8 CPU-ядер + GPU) — bottleneck.
- **Решение**: lock-free ленты через `crossbeam::epoch` или атомарные операции. `AtomicPtr<PageTable>` + copy-on-write при resize. Запись создаёт новую версию, старая жива пока readers не закончат (epoch-based GC).
- **Для кого**: Position/Velocity — «горячие» ленты, где lock-free must have.
- **Примечание**: `RwLock` не обязан быть bottleneck — `read_lane` возвращает `RwLockReadGuard`, contention возникает только при реальной записи. Поэтому lock-free стоит делать **опционально**: `LockFreeLane<T>` и `RwLockLane<T>` сосуществуют, выбор за профилированием. Если contention < 5–10% — `RwLock` эффективнее и проще.

## 17. Hot/Cold Data Splitting (память + кэш)

- **Проблема**: `Entity { position, velocity, health, inventory, dialog_tree }` — `inventory` используется в 1% кадров, но загружается в кэш при каждом обходе `Position`.
- **Решение**: макрос `#[cold]` отделяет редко используемые поля в отдельные «медленные» ленты. Hot-данные лежат компактно в кэш-линиях.
- **Экономия**: кэш-линия содержит только «живые» данные, мусор не отсеивается.
- **Примечание**: автоматический анализ частоты доступа к полям в compile-time невозможен — у макроса нет информации о runtime-паттернах. Поэтому split делается **явно**, через атрибут `#[cold]` от пользователя. Автоматический split — только через runtime-профилирование (в связке с Temporal Coherency Sort, идея 22), которое переупорядочивает данные постфактум.

## 18. Prefetch Intrinsics (скорость CPU)

- **Проблема**: CPU ждёт RAM 100–200 циклов при первом доступе к следующей странице памяти.
- **Решение**: явный `_mm_prefetch` в итераторе — команда CPU подтянуть следующие кэш-линии заранее.
- **Прирост**: 10–20% на sequential access. Пользователь не видит unsafe — макрос скрывает.

## 19. Batch API для скриптов (zero overhead)

- **Проблема**: Python/JS скрипт делает `entity.position.x += 1` в цикле — каждое обращение = FFI-вызов + проверка bounds.
- **Решение**: `engine.batch_add("Position", "x", 1.0)` — 1 FFI-вызов, внутри `rayon par_iter_mut`. Скриптовый движок парсит batch-запрос, генерирует closure, передаёт в Rust.
- **Прирост**: 100k FFI → 1 FFI = разница между 16 ms и 0.05 ms.

## 20. Component Packing / SoA внутри компонента (память)

- **Проблема**: `struct Transform { position, rotation, scale }` — 40 байт. Система `update_position` читает только `position`, но тащит 28 лишних байт.
- **Решение**: макрос автоматически раскладывает структуру на под-ленты: `ComponentStore<Vec3>` (position), `ComponentStore<Quaternion>` (rotation), `ComponentStore<Vec3>` (scale). Система видит только нужную ленту.
- **Tradeoff**: `get_mut::<Transform>()` собирает 3 ленты в прокси-структуру, но это редкая операция.

## 21. NUMA-Aware Allocation (масштабируемость)

- **Проблема**: на 32+ ядерных Threadripper'ах `Vec<T>` выделяется на одном NUMA-узле, ядра с другого узла лезут через Infinity Fabric — latency ×2.
- **Решение**: `ComponentStore<T>::with_numa_affinity(node_id)` через `libc::mbind` (Linux) / `VirtualAllocExNuma` (Windows).
- **Для кого**: MMO-серверы, где 1 ядро = 1 shard и память должна быть «рядом».

## 22. Temporal Coherency Sort (физика/рендеринг)

- **Проблема**: сущности созданы хаотично. Физика и рендеринг обрабатывают их последовательно, кэш не «привыкает».
- **Решение**: после N кадров анализировать «горячие кластеры» (игрок + 50 ближайших врагов) и перемещать их данные в начало dense-массива.
- **Прирост**: 20–40% на сценах с фокусом (камера видит 100 объектов из 100k).

## 23. Compute Shader Pre-warm (GPU latency)

- **Проблема**: первый запуск WGSL-шейдера = компиляция драйвером + pipeline creation — 50–200 ms freeze.
- **Решение**: PSO-кэш — `HashMap<(TypeId, TypeId), wgpu::ComputePipeline>`. При старте создаём все известные пайплайны. `wgpu` поддерживает сериализацию кэша на диск — второй запуск мгновенный.

## 24. HVM2-derived: Strong Confluence, LEAK-паттерн, интеграция

### 24.1 Strong Confluence как гарантия движка

- **Идея (из HVM2)**: Interaction Combinators обладают сильной конфлюэнтностью — порядок редукции не влияет на результат. Та же гарантия нужна игровому движку: параллельные системы должны быть детерминированы независимо от числа ядер.
- **Реализация**: все макросы `#[smart_pipeline]`, `#[gpu_pipeline]`, `for_each_entity!` должны гарантировать, что `rayon::par_iter_mut()` и GPU-диспетчеризация дают идентичный результат при любом порядке обработки элементов.
- **Проверка**: тесты с `RAYON_NUM_THREADS=1` и `RAYON_NUM_THREADS=32` должны давать побитово одинаковый output для одних и тех же входных данных.
- **Почему важно**: детерминизм критичен для replay-систем, сетевой синхронизации и отладки. Если `for_each_entity!` не strongly confluent — баги будут воспроизводиться только на определённом железе.

### 24.2 LEAK-паттерн для GPU-блоков (конкретизация «Инструкции вместо данных»)

- **Идея (из HVM2)**: GPU-потоки работают в быстрой shared memory (L1-кэш), а наружу «протекают» только ссылки на результаты, которые нужны другим блокам. Сам HVM2 называет это LEAK-интеракцией.
- **Применение в движке**: dense-массив `ComponentStore<T>` разбивается на блоки по 64–256 элементов. Каждый блок — это `wgpu::ComputePass`, работающий в shared memory. Наружу возвращаются только dirty-флаги для синхронизации с CPU.
- **Преимущество**: минимум глобальных обращений к VRAM, максимум локальной пропускной способности. Паттерн перекликается с Chunked Iteration (идея 15), но для GPU.
- **Реализация**: макрос `#[gpu_pipeline]` генерирует код, который автоматически делит `data` на чанки по числу потоков в warp/wavefront, обрабатывает в local memory и записывает результат обратно.

### 24.3 HVM2 / Bend как опциональный compute-бэкенд (future work)

- **Идея**: вместо кастомной генерации WGSL через `syn` (DSL-подмножество) — использовать HVM2 как runtime для pure-функций. Bend-код компилируется в HVM2 и исполняется на CPU (C-бэкенд) или GPU (CUDA-бэкенд).
- **Когда**: после появления FFI в Bend (в планах HOC). Без FFI Bend не может читать/писать Sparse Set.
- **Применение**: математика физики, процедурная генерация, трансформации деревьев (коллизии, LOD) — всё, что не требует IO и укладывается в pure functional модель.
- **Tradeoff**: HVM2 пока CUDA-only (GPU) и 24-bit числа. Для production-движка — долгосрочная ставка. Но как скриптовый язык для прототипирования — Bend уже сейчас интереснее Rhai/Rune для чистых вычислений, т.к. автоматически параллелится.

## 25. Открытые стандарты (OpenPBR, MaterialX) и плагинная архитектура

### 25.1 OpenPBR Surface Model

- **Идея**: использовать открытый стандарт [OpenPBR](https://openpbr.org) как единую модель поверхностного затенения. Металличность, шероховатость, clearcoat, sheen, subsurface, transmission — всё по спецификации, совместимо с USD, MaterialX и индустриальными DCC-инструментами.
- **Реализация**: OpenPBR → WGSL-шейдеры через `naga` + автогенерация `wgpu::BindGroup` из `ComponentStore<Material>`.
- **Зачем**: не изобретать свой PBR, а взять готовый стандарт, который уже принят в VFX и AAA.

### 25.2 MaterialX

- **Идея**: поддержка формата [MaterialX](https://materialx.org) (нод-графы для материалов, стандарт от ILM/Autodesk/Apple).
- **Реализация**: парсер `.mtlx` → AST → компиляция в WGSL-шейдеры → `wgpu::ShaderModule`. Пользователь загружает MaterialX-файлы как ассеты, движок сам компилирует.
- **Зачем**: совместимость с профессиональными пайплайнами. Художники готовят материалы в Substance/Blender → экспорт в `.mtlx` → движок.

### 25.3 Плагинная архитектура физики

- **Идея**: встроенная лёгкая физика (Sweep-and-Prune, constraints solver, capsule/box/sphere colliders) покрывает 80% инди-сценариев. Через единый трейт `PhysicsEngine` подключаются Rapier (для точности), Jolt (для AAA), PhysX (для legacy).
- **Архитектура**:
  ```rust
  trait PhysicsEngine {
      fn step(&mut self, dt: f32);
      fn raycast(&self, origin: Vec3, dir: Vec3) -> Option<Hit>;
      fn add_body(&mut self, body: RigidBody) -> BodyHandle;
      // ...
  }
  ```
- **Будущее расширение**: физика выносится в отдельный поток/процесс (IPC) для максимальной производительности на многоядерных системах. SIMD-солвер + выделенный physics-тред.

### 25.4 Плагинная архитектура рендера

- **Идея**: собственный рендер на `wgpu` (с OpenPBR + MaterialX) — реализация по умолчанию. Через трейт `RenderBackend` можно подключить любой другой рендер (для консольного порта, HDRP, специфического железа).
- **Архитектура**:
  ```rust
  trait RenderBackend {
      fn begin_frame(&mut self);
      fn draw_mesh(&mut self, mesh: &Mesh, material: &Material, transform: &Mat4);
      fn end_frame(&mut self) -> FrameHandle;
  }
  ```
- **Зачем**: разделение логики сцены и рендера. Сцена живёт в Sparse Sets, рендер — это просто view на данные.

### 25.5 Физический движок: собственный лёгкий vs внешний

- **Встроенная физика**: Sweep-and-Prune broadphase, позиционный/velocity-based constraints solver, AABB sweep для raycast/shapecast. Только box/sphere/capsule коллайдеры. Минимум зависимостей.
- **Внешняя (Rapier/Jolt/PhysX)**: подключается через `PhysicsEngine` trait. Используется когда нужны mesh colliders, continuous collision detection, breakable joints, сложная деформация.
- **Выбор**: статический профайлер (Phase 3) решает: 100 box-коллайдеров → встроенный, сложная сцена с mesh-коллизиями → Rapier.
- **Future**: выделенный physics-тред с SIMD-солвером, IPC-связь через shared memory, бенчмарк <1 ms на 10k тел.

## 26. Аудиосистема — Sparse Sets для звука + DSP

- **Звук как компонент**: `AudioSource { clip_id, volume, pitch, spatial, playing }` и `AudioListener { gain }` — обычные ленты в `SmartStore`. Сущность со звуком = `Entity { Position, AudioSource }`.
- **Spatial audio**: система читает `Position` сущности + `Position` камеры (из `AudioListener`), считает rolloff и панораму — всё через `for_each_entity!` и `rayon`.
- **Аудиограф**: микшер в реальном потоке (OS-тред с высоким приоритетом). DSP-эффекты (reverb, EQ, compression) — цепочка чистых функций, читающих из лент.
- **GPU Audio (future)**: свёртка, FFT, спектральный анализ — через `#[kernel]` на wgpu. Латентность 5–10 мс приемлема для музыки и окружения.
- **Бэкенды**: `cpal` (Desktop: ALSA/WASAPI/CoreAudio), Web Audio API (WASM), выделенный real-time поток.
- **Ассеты**: `.wav`/`.ogg`/`.mp3` через `symphonia` → `AssetStorage`. Стриминг длинной музыки через кольцевой буфер.

## 27. Render Graph — гибрид Forward+Deferred через граф пассов

> Дизайн и фазы 0–4 реализованы; подробный implementation note: [`docs/rendering/render-graph.md`](docs/rendering/render-graph.md). Исходная дата дизайна: 2026-08-10.

- **Проблема**: не могли определиться Forward vs Deferred. Ответ исследования: выбрать не нужно — нужен слой оркестрации пассов.
- **Что это**: render graph — DAG, где пассы = узлы, зависимости по ресурсам = рёбра. Глобальное знание о кадре → transient-ресурсы, переиспользование памяти, culling пассов, расширяемость. Не третья техника рендеринга, а каркас, на котором гибрид (deferred неопрачные + forward прозрачные) собирается как конфигурация.
- **Состояние Ornis**: гибрид уже есть императивно — `renderer.rs` (~1550 строк): gbuffer (5 MRT) → lighting → forward → composite. Не хватает оркестрации.
- **Оговорка wgpu**: барьеры/layout transitions wgpu делает сам; ценность графа для Ornis — lifetime ресурсов (gbuffer → transient), декларативность, расширяемость. Тяжёлый bake Granite (алиасинг памяти, async compute) на wgpu не переносится буквально.
- **План**: лёгкий immediate-граф (паттерн Frostbite/Ponies&Light): каркас → обёртка 4 существующих пассов → gbuffer transient → первый новый узел (SSAO/блум) → переключатель forward/hybrid/deferred.
- **Референсы**: Frostbite FrameGraph (GDC 2017), Granite deep dive (themaister), Ponies & Light, rafx (Rust), Bevy render_graph, wgpu-rendergraph (wasm webgl/webgpu).

## 28. Unified Scheduler — «третий путь» между Frostbite FrameGraph и Bevy 0.19

> ⚠️ **Долгосрочное направление.** Не план на ближайшие месяцы, а целевая архитектура на горизонте лет. Режим проекта — «в долгую, никуда не торопимся». Дата: 2026-08-14.

**Контекст.** В 0.19 (июнь 2026) Bevy полностью убрал `RenderGraph` API — render-пассы теперь обычные ECS-системы в `Core3d` / `Core2d` schedules с ордерингом через `.before()` / `.after()`. Frostbite FrameGraph, наоборот, 15 лет оттачивал свой graph как отдельный framework с runtime-узлами/рёбрами/slot'ами. У каждой модели фундаментальный пробел:

| Свойство | Frostbite FrameGraph | Bevy 0.19 | Цель |
|---|---|---|---|
| Transient-ресурсы, aliasing | ✅ автоматически | ❌ нет анализа | ✅ |
| Один scheduler на всё | ❌ отдельный framework | ✅ `Schedule` + системы | ✅ |
| Compile-time валидация | ❌ runtime graph | ✅ типы систем | ✅ (больше) |
| Параллелизм по доступу к данным | ❌ линейный | ✅ автоматически | ✅ |
| Дебагабельность | ❌ отдельный инструмент | ✅ обычный stack trace | ✅ |
| Memory budget как first-class цель | ❌ нет | ❌ нет | ✅ |

«Третий путь» — взять сильные стороны обеих: один scheduler (Bevy) + автоматический lifetime/aliasing-анализ (Frostbite) + типизированные ресурсы на уровне сигнатур. Три идеи ниже — компоненты этого пути.

### 28.1 Borrow-checker-driven scheduling (главная идея)

Система объявляет, что ей нужно, **через тип параметра** — как `&Texture` или `&mut Buffer` в Rust. Scheduler:

- **выводит граф зависимостей** из сигнатур всех систем в `Schedule` (как Bevy 0.19 уже делает для ECS-данных);
- **вычисляет lifetime-окна** для каждого ресурса (как `RenderGraph::compute_layout` сейчас — `first_use..last_use`);
- **пулит/алиасит** непересекающиеся по lifetime ресурсы в один физический пул (как `GraphExecutor::pool` сейчас);
- **проставляет GPU-барьеры** автоматически, если ресурс переходит из write в read между пассами.

Ключевое: **графа как структуры данных нет**. Граф — проекция типов. Добавить пасс = написать систему с правильной сигнатурой. Валидация в основном compile-time, runtime нужен только для аллокации и barrier'ов.

**Что меняется в Ornis**: `RenderGraph` (imperative builder с узлами/рёбрами/slot'ами, `crates/render/src/render_graph.rs:312`) и `PassBuilder` постепенно сворачиваются в **набор систем с типизированными ресурсами** в одном `Schedule`. `RenderGraph3D::new_with(...)` и `add_pass("gbuffer").write(ids.albedo)...` уходят; пасс = функция с сигнатурой.

### 28.2 Один мир, без Extract-фазы

**Проблема Bevy 0.19**: extract-фаза копирует данные из `app world` в `render world`, потому что иначе они конфликтуют за `&mut World`. Это bandwidth и код, которых можно избежать.

**Решение**: разрешить системе иметь доступ к **подмножеству мира через query-параметры** (как сейчас для компонентов через `Query<...>`), и пусть scheduler доказывает, что одновременный доступ безопасен. Один `World`, в нём всё: `SmartStore`-ленты, GPU-ресурсы как `Component` на singleton entity, рендер-данные как `Component` — без второго `World`.

**Что меняется в Ornis**: текущая связка `RenderGraph3D` (отдельный контейнер поверх `RenderGraph` + `GraphExecutor`) и `RenderContext` (отдельный контейнер для `device`/`queue`/`encoder`) сворачивается в **ECS-системы, которые берут `Res<Device>`, `Res<SurfaceConfig>`, etc., и пишут в те же ленты, что и физика**. Никаких копирований. Граница между «CPU-стороной» и «GPU-стороной» остаётся только как соглашение о типах, не как физический разрыв.

> **Переходный статус 2026-08-27:** native и WASM уже используют общий
> library-level `RenderWorld`/`Engine`/`RenderExtract` data-flow и один
> `RenderFrame3D`/`FramePlan` pass path. Серверный `EditorWorld` и браузерный
> `RenderWorld` находятся в разных контекстах, поэтому versioned JSON
> serialization boundary сохраняется намеренно; это не считается нарушением
> идеи единого *логического* World. Полное слияние render/physics/input в
> верхний scheduler и устранение отдельной extraction boundary остаются
> долгосрочной целью этого раздела.

### 28.3 Memory budget как first-class цель оптимизации

Сейчас и Frostbite, и Bevy оптимизируют по скорости выполнения. Никто не говорит: «у меня 64 МБ на GPU-текстуры — сделай лучший кадр в этом бюджете». А это **именно то, что нужно мобильным и tier-1 консолям** — и то, что позволяет алиасить более агрессивно.

**Идея**: scheduler принимает `Budget { gpu_textures: 64.mb, transient_pool: 32.mb, … }` и при компиляции графа минимизирует **пиковое использование памяти** в рамках бюджета. NP-трудная задача в общем случае, но для дерева фаз с фиксированным порядком (как сейчас в Ornis) — полиномиальная (interval partitioning + цветовое кодирование).

**Что меняется в Ornis**: `GraphExecutor::texture_budget()` (`crates/render/src/graph_frame.rs:75`), который сейчас просто суммирует байты, становится **входным параметром scheduler'а**. Планировщик говорит, какой G-buffer и в каком порядке пулить, чтобы уложиться в бюджет. Можно проверять на этапе `build()`: «при таком размере пула у тебя composite не поместится — увеличь бюджет или убери SSAO».

### Честная оценка стоимости

Это **годы работы**, не проект на пару месяцев. Frostbite 15 лет оттачивал свой graph; Bevy 8 лет — свой scheduler. Чтобы собрать третий путь, нужны:

1. Глубокая интеграция type system и scheduler'а (месяцы прототипирования).
2. Реальный production-нагрузки (мобильные tier-1, консоли, AAA) — без них дизайн-решения оказываются теоретическими.
3. Постепенная миграция существующего кода (Ornis: `RenderGraph` ~470 строк, `graph_frame.rs` ~800 строк, `Renderer3D` ~1550 строк).

### Эволюционный путь (от текущего состояния Ornis)

Чтобы не строить «с нуля», можно идти итеративно. Каждый шаг — самостоятельный выигрыш, не зависит от следующего:

1. **Ближайшее (недели)** — кеш `GraphLayout` в `RenderGraph`. Инвалидация по `(surface_size, Technique, bloom, сигнатура read/write множеств)`. Дёшево, окупается сразу: убирает `compute_layout` с горячего пути кадра.
2. **Среднесрочно (месяцы)** — вынести `RenderGraph` в стиле `graph_frame.rs` (pass = struct + handler), сделать так, чтобы пасс мог быть **объявлен как система** с типизированной сигнатурой, а не через builder. Прямой шаг к «один scheduler».
3. **Долгосрочно (годы)** — посмотреть, можно ли отказаться от `RenderGraph` как структуры данных и заменить его на системный DAG с first-class transient-ресурсами (идея 28.1). Если получится — Ornis попадает в «третий путь». Если нет — у движка останется работающий RenderGraph и понимание, почему.

Собственно, **это и есть тот scheduler graph, который был задуман как «надстройка над RenderGraph»**, но эволюционно, а не как greenfield-проект.
